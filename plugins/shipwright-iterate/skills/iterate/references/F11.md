# F11 — Push Branch, Open PR & Verify

**Leak-guard first** — confirm the run never touched the main repo
working tree (snapshot-and-diff against the B1a Step-1 snapshot):

```bash
uv run "{shared_root}/scripts/checks/check_iterate_isolation.py" \
  --project-root "{project_root}" --run-id "{run_id}" --stage f11
```

Non-zero exit = **STOP**.

**Refresh-if-behind guard (Option A — serial integrate, never server-side).**
GitHub auto-merge does a server-side 3-way merge and NEVER runs the
regenerate-at-merge resolver, so a branch that fell behind `origin/<default>`
while open would merge **stale** (Group-E staleness) or stall **DIRTY** on the
regenerated snapshots. Bring the branch current through `ensure_current.py`
FIRST (fetch → if behind: merge → churn-reconcile → regenerate snapshots →
commit) so the PR arms auto-merge from a current, already-regenerated tree. A
branch that is already current is a clean no-op (nothing fetched-merged-committed).

```bash
guard=$(uv run "{shared_root}/scripts/tools/ensure_current.py" \
  --project-root "{project_root}" --run-id "{run_id}" \
  --reason "F11 pre-merge refresh: {run_id}") || {
    echo "$guard"
    echo "STOP: ensure_current failed (non-churn/source conflict?) — resolve by hand, then re-run F11."
    exit 1
  }
echo "$guard"
```

This runs BEFORE the push below, so the single `git push -u` ships any integrate
commits. A non-churn (source) conflict exits non-zero — the same hard safety
gate as the resolver — and **STOPS** the run.

**Shared-branch health, before the arm.** Merging a green branch onto a red
`origin/<default>` makes the next run on that branch red too, and the blame
lands on the wrong change — the attribution chain this repo depends on breaks at
exactly the moment it is needed.

```bash
uv run "{shared_root}/scripts/tools/main_health.py" --project-root "{project_root}"
```

`0` green / `3` running → arm as normal. `4` unknown → arm, and surface the
unknown in the F12 summary (unknown is never green). `2` red → **repair it
first**, as its own small `fix(main): …` PR, per
[main-repair](references/main-repair.md); the repair is claimed by **creating**
the ref `iterate/fix-main-<sha12>` — a same-SHA `git push` succeeds for both
racers and locks nothing — and an existing claim means someone else already has
it, so arm and move on. `5` escalate → a finding-class workflow is red: file the
card (`escalate.keys` is the idempotency key), then arm. This runs BEFORE the
arm below, not after: a PR armed onto a red base merges the moment its own
checks pass.

**Push the iterate branch and open a PR.** An iterate run NEVER checks
out, merges, or pushes the default branch — that races every other
parallel iterate. One iterate = one branch = one PR.

```bash
default_branch=$(git -C "{project_root}" symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's@^refs/remotes/origin/@@' || echo main)
git -C "{project_root}" push -u origin "iterate/{slug}"
# gh has no `-C` analog — it acts on the cwd's repo. cd into the worktree
# so gh can never operate on the main repo even if the shell cwd drifted.
cd "{project_root}"
gh pr create --base "$default_branch" --head "iterate/{slug}" \
  --title "<type>(<scope>): <description>" \
  --body "<summary>

## Empirical Test Completeness
<derived from iterate_latest.test_completeness — e.g.>
Testable: N · Tested: N · Untestable (structural reason): M · Untested-but-testable: 0 ✅

Run-ID: {run_id}"

# --- Arming happens inside the delivery ladder (see "Delivery" below) ---
# Do NOT arm here. `deliver_pr.py` arms, classifies a refusal, and then
# either watches (the host will merge) or merges here (the host CANNOT).
# Arming and watching had to become one step because the decision that
# joins them — "will anything ever merge this?" — is only answerable from
# the arm's outcome (iterate-2026-07-31-f11-delivery-truth).
head_branch="iterate/{slug}"
pr_url=$(gh pr view "$head_branch" --json url -q .url)
```

**Empirical Test Completeness line (always, small+).** Render one line from
`iterate_latest.test_completeness` into the PR body so the reviewer reads the
answer to *"did you test everything testable?"* without asking. `Untested-but-testable`
is `0` by construction — the F11 verifier (below) fails closed otherwise.
At trivial complexity emit `Completeness: n/a — <justification>`.

If `iterate/{slug}` diverged from `origin/<default>` since B1a fetched it
(another iterate merged meanwhile), the **refresh-if-behind guard above**
(`ensure_current.py`) already merged + regenerated the derived snapshots — a
**merge**, not a rebase, because only the merge path runs the regenerate-at-merge
resolver (a rebase replays your commits but never re-derives the churn snapshots,
so it would merge stale). That guard is the deliberate, single conflict point.
**The iterate is NOT done when the PR is armed — it is done only when the PR is
_delivered_: MERGED with all Required Checks GREEN**, confirmed by the **Delivery**
step below. Arming and walking away is "shoot and forget"; a check can fail
afterward and the PR sits BLOCKED. Who performs the merge is decided by what the
host can do, and only ever by that — see the ladder below.

**Update session handoff** to reflect completed state. Pass `--reason`
so the handoff shows what caused the regeneration instead of the
default `context compaction`:

```bash
uv run "{shared_root}/scripts/tools/generate_session_handoff.py" \
  --project-root "{project_root}" --preserve-canon-marker \
  --reason "iterate completion: {run_id}"
```

`--preserve-canon-marker` is not optional. This write runs **after** F5b stamped
the iterate canon marker, so without it the marker is deleted at the very end of
every iterate — and because all eight canon phases read this one file, Canon C3
then reports "no canon marker" for every one of them on every Stop until some
phase closure rewrites it. It must not pass `--canon-marker` instead: this is a
post-commit refresh, not the canon closure, and F5b already recorded that.

**Gate check:** F5b records the `work_completed` event into **this
worktree's own** `shipwright_events.jsonl` (the per-tree, PR-committed model —
`events_log.resolve_events_path` returns the literal `{project_root}` copy),
and F6 stages it so it ships in the PR. The deterministic verifier below checks
this authoritatively via `check_events_has_commit`, which — when the log is
tracked — asserts the event is in the **committed HEAD blob**, not merely the
working copy (AC4). So the event MUST be at `{project_root}/shipwright_events.jsonl`
AND committed by F6; if F6 forgot to `git add` it, the verifier fails closed.

**Deterministic verifier.** After the gate check, run the
finalization verifier and fail the iterate run on red:

```bash
uv run "{shared_root}/scripts/tools/verify_iterate_finalization.py" \
  --run-id "{run_id}" \
  --project-root "{project_root}" \
  --commit "$(git -C "{project_root}" rev-parse HEAD)"
```

Exit 0 = green (or warnings only), exit 1 = at least one required
artifact missing. Add `--strict` to treat warnings as errors.

This run includes `check_test_completeness_ledger` (small+): it fails closed
when any behavior in `iterate_latest.test_completeness` is testable-but-untested,
an `untestable` row lacks a closed-vocabulary `reason_code`, or the
enumeration falls short of the AC count. That is the gate that makes the
operator's pre-merge "did you test enough?" question unnecessary.

It also includes `check_review_record` (small+; skipped at trivial): the run's
`.shipwright/planning/iterate/{run_id}/reviews.json` must exist and hold NO
review type still `pending`. All six — `self` · `plan` · `code` · `doubt` ·
`external_code` · `spec` (Stage 1), all under `reviews` — are materialized up
front and each is closed by the pass that owns it; a pass that did not run is
closed `not_run` / `not_applicable` with a `--disposition` naming the rule (a
bare "skipped" is rejected). A `spec` row absent from **both** `reviews` and the
retired `gates` sibling counts as unanswered: the schema tolerates the absence
so older records stay readable, and a live run gets nothing from that — it
cannot dodge the row by declining to write it.

Two further ways this gate can fail, both about substance rather than bookkeeping:

- **An evidence-free code review.** At medium+ a `code` / `external_code` row
  recorded `completed` must carry findings, a non-blank `provider`, a non-blank
  `raw_excerpt`, or a `recorded_by` naming an adapter other than `none`.
  `--status completed` with `--from` omitted produces a row with none of them.
  Repair: re-record handing over the reviewer's reply, with `--force`.
- **Stage 2 without Stage 1.** A `code` row recorded `completed` while `spec` is
  not `completed` fails — the spec-compliance HARD-GATE must pass before the
  code-reviewer runs. The `spec` row is held to the same evidence bar. Repair:
  `record_review_pass.py record --run-id {run_id} --review-type spec --status
  completed --from code-reviewer --payload-file <reply>`. `external_code` is
  outside this rule by design.

Fails closed on a missing, unreadable, or schema-invalid record, and on one whose
`run_id` names a different run. Remediation is printed with the exact command per
outstanding type; a run that predates the record closes everything at once with
`record_review_pass.py close-missing`. **`close-missing` is for a run that
predates the record — not for a cascade that was never asked about.** A `code`
row still outstanding at F11 means Step 8's cascade did not run. If the only obstacle was a
session policy AND the project's `CLAUDE.md` grants review subagents standingly,
there was never anything to ask — spawn them. **The four blockers in
`iteration-reviews.md` step 0 are unaffected by any grant**: a runner with no
`Agent` tool still cannot spawn, whatever CLAUDE.md says. Otherwise, if the only
obstacle is a session policy, ask the operator now instead of closing the row, because such a policy is conditional and is **not** one of the four
blockers (`iteration-reviews.md` → "When the internal reviewer cannot run",
step 0). Every observed lapse of this pass was decided here, at closing time,
not at Step 8. The point of the gate is that an empty
Review row in the Mission view always means "genuinely not run", never "nobody
wrote it down".

It also includes `check_iterate_no_direct_decision_log`: an iterate whose commit
modified `.shipwright/agent_docs/decision_log.md` fails closed — record the ADR as
an F3 decision-DROP (`write_decision_drop.py`), never append to `decision_log.md`
directly (the `ADR-NNN` is assigned at `/shipwright-changelog` release). Paired
with a stricter `check_adr_in_iterate_history` that accepts a run-id ADR identity
only when the drop actually carries the ADR or a `Run-ID:` line is in
`decision_log.md`.

**Delivery — the iterate is DELIVERED only when the PR is MERGED + green.**
NEVER arm auto-merge (or push) and declare "done": that is "shoot and forget" —
a Required Check can fail afterward and the PR sits BLOCKED, un-merged, red.

**One delivery bar, three repositories.** `deliver_pr.py` arms, and then decides who
merges from what the host can actually do. The bar never moves; only the actor does.

```bash
uv run "{shared_root}/scripts/tools/deliver_pr.py" \
  --pr "$pr_url" --repo "<owner>/<name>" \
  --project-root "{project_root}" --run-id "{run_id}" \
  --head-branch "iterate/{slug}" --base-branch "$default_branch" \
  --verified-commit "$(git -C "{project_root}" rev-parse HEAD)"
# Fail CLOSED: ONLY exit 0 (merged + green) is "delivered". Every other outcome
# STOPS the run (exit 1) — never fall through and claim "done".
case "$?" in
  0) echo "DELIVERED — PR merged + all Required Checks green. The tool's own line names WHO merged it and how many checks the host ran; repeat that rather than paraphrasing it as 'CI green' when the host ran none." ;;
  2) echo "NOT DELIVERED — a Required Check FAILED. Diagnose (gh run view --log-failed <run>), FIX, re-push, then re-run delivery. The iterate is NOT done." ; exit 1 ;;
  3) echo "NOT DELIVERED — PR was CLOSED unmerged." ; exit 1 ;;
  4) echo "NOT DELIVERED — still PENDING at the timeout. Re-run delivery to keep waiting; do NOT claim 'done'." ; exit 1 ;;
  5) echo "NOT DELIVERED — the host could not be read (gh error). Verify + re-run before claiming delivery." ; exit 1 ;;
  6) echo "NOT DELIVERED — no merger can exist: the host cannot arm auto-merge AND self-merge is not permitted here. Merge it by hand, or set SHIPWRIGHT_ITERATE_SELF_MERGE=1. Re-running changes NOTHING." ; exit 1 ;;
  7) echo "NOT DELIVERED — delivery refused (identity mismatch, re-verification red, or the host refused the merge). Read the reason; do NOT retry blindly." ; exit 1 ;;
  *) echo "NOT DELIVERED — unrecognised delivery outcome. Verify by hand before claiming delivery." ; exit 1 ;;
esac
```

**The ladder, and why each rung exists.**

0. **Confirm the PR is this run's** — open, head `iterate/{slug}`, base the default
   branch — *before* the arm. `--auto --squash --delete-branch` is itself a mutating
   command: on a stale PR number or a reused checkout it would merge and delete
   somebody else's branch the moment their checks went green. A PR that is already
   MERGED or CLOSED is **reported** with that state's own verdict rather than refused,
   so re-running delivery after it landed cannot report a failure.
1. **Arm** `gh pr merge --auto --squash --delete-branch`, `iterate/*` only — a
   human-authored PR never reaches this prose and never self-arms. Armed ⇒ the host
   merges when green and the tool only watches. Unchanged behaviour.
2. **A refusal is classified from facts, never from GitHub's wording** —
   `allow_auto_merge` on the repository and `protected` on the base branch, both
   readable without admin rights. `protected` is used rather than the rulesets
   endpoint because that endpoint reports rulesets ONLY, so a repo on *classic*
   branch protection answers `[]` while arming works perfectly. Anything that is not
   one of the two structural answers below — an unreadable fact, a draft PR, a
   conflict — is transient: keep watching, exactly as today. **An unreadable picture
   never licenses a merge.**
3. **Arming impossible ⇒ deliver it here, but ONLY on an unprotected base:** wait for
   green → refresh if behind or conflicted → **verify the head that will merge** →
   merge pinned to that commit → confirm `MERGED`.

   A base that IS protected while the repo's auto-merge setting is merely off gets
   **exit 6**, not a self-merge. The protection expresses required reviews and checks;
   an iterate usually runs with the operator's own token, which on their own repository
   may bypass exactly those; and "the host will refuse us" is an assumption nobody has
   tested for a bypass-capable actor. The remedy there is one checkbox — *Settings →
   General → Pull Requests → Allow auto-merge* — not a new authority.

Rung 3 exists because on a base *without* branch protection the arm fails outright
(`Protected branch rules not configured for this branch`) and then **nothing** merges
the PR: every iterate on such a repo ended not-delivered after the 1800-second
timeout, and a private repo on GitHub Free cannot have rulesets at all, so it could
never be delivered to. Measured on throwaway PR #501.

**Rung 3 is stricter than `--auto`, not looser.** `ensure_current` exists because the
host's server-side merge cannot run the regenerate-at-merge resolver, so a branch
that fell behind merges stale (Group-E). Arming narrows that window but cannot close
it — `--auto` merges the moment checks pass, however far the branch has drifted by
then. Here the moment of merging is ours, so the refresh happens immediately before
it. Two guards follow from that:

- **What merges is what was verified.** Pass `--verified-commit` — the commit the
  verifier above actually ran on. Any other head, whoever produced it, is verified again
  before it may merge, and red **STOPS** delivery. That covers a refresh made *during*
  the wait, a commit pushed by anything else sharing the worktree, **and** a re-run after
  a previous invocation left the branch on a commit its own re-verification rejected.
  The merge is then issued with `--match-head-commit`, so the *host* enforces the pin.
  Up-to-dateness is re-read at the moment of merging too, not only at the last poll.
- **Checks do not vanish.** Straight after a refresh push the new head's rollup can
  be empty, which would read as "green, zero checks". Readiness holds at pending
  until at least as many checks report as were seen before.

A `needs:`-skipped required job (Tier-1/2 `PR Review`) counts as a pass, not a
failure — for the watch verdict and for readiness alike, which is why both read the
rollup through one shared helper.

**Self-merge is on by default and can be switched off** with
`SHIPWRIGHT_ITERATE_SELF_MERGE=0`; an unrecognised value fails **closed**. Switched
off, a repo that cannot arm gets exit 6 **immediately** instead of waiting half an
hour for a merger that cannot exist. **Under a campaign
(`SHIPWRIGHT_ITERATE_AUTOMERGE=0`)** nothing is armed and nothing self-merges — the
orchestrator merges each PR in turn, interleaved-serial (campaign-mode.md step 3g);
the same "delivered = merged" bar applies per sub-iterate.

**Say who merged it.** When Shipwright performed the merge, the F12 summary must name
that *and* how many checks **passed**. Zero is legitimate on an unprotected repo — the
local suite is then the only evidence — but it must never be reported as though the host
confirmed anything, and a rollup of nothing but skipped jobs counts as zero, not three. For plugin/`shared/*` changes, "delivered to the
runtime" additionally requires the post-merge `update-marketplace.sh` cache sync.

`watch_pr_delivery.py` remains the read-only diagnostic: run it with `--once` to ask
"why is this PR stuck?" with no risk of merging anything.
