# F0 — Fresh Verification Gate

**Leak-guard first.** Confirm the run is still isolated —
`{project_root}` is an iterate worktree and nothing leaked into the
main repo working tree:

```bash
uv run "{shared_root}/scripts/checks/check_iterate_isolation.py" \
  --project-root "{project_root}" --run-id "{run_id}" --stage f0
```

Non-zero exit = **STOP**: either the run is not executing in a
worktree, or it wrote into the main tree (compared against the B1a
Step-1 snapshot). Investigate and revert before continuing.

**Then the mirrored merge gates — where the project has them.** Some
repositories carry a pre-flight that runs the bespoke merge guards their
CI runs and nothing else runs locally. Run it *before* the suite: it is
seconds against the suite's minutes and it fails for cheap structural
reasons, so learning about it first is the whole point. Non-zero exit =
**STOP**.

```bash
# POSIX / Git-Bash
if grep -q "SHIPWRIGHT_MIRRORED_MERGE_GATES" \
      "{project_root}/scripts/verify_local.py" 2>/dev/null; then
  ( cd "{project_root}" && uv run scripts/verify_local.py )
fi
```

```powershell
# PowerShell — the primary shell on Windows, where this repo is developed
$gate = "{project_root}/scripts/verify_local.py"
if ((Test-Path $gate) -and
    (Select-String -Path $gate -Pattern "SHIPWRIGHT_MIRRORED_MERGE_GATES" -Quiet)) {
  if (-not (Get-Command uv -ErrorAction SilentlyContinue)) {
    throw "uv is not on PATH — the mirrored merge gates could not run. STOP."
  }
  Push-Location "{project_root}"
  try {
    uv run scripts/verify_local.py
    if ($LASTEXITCODE -ne 0) {
      throw "verify_local.py failed ($LASTEXITCODE) — STOP, do not continue to F1"
    }
  } catch {
    throw "the mirrored merge gates did not pass: $_ — STOP, do not continue to F1"
  } finally { Pop-Location }
}
```

**The guard is on identity, not on a path.** `scripts/verify_local.py` is
not a distinctive name. Guarding on existence alone would mean a consumer
project that happens to carry a file at that path gets an arbitrary local
script executed by an agent, from a prompt Shipwright ships, under
"non-zero = STOP" semantics — a foreign script's exit code halting the
user's run for a reason that is not a defect, which is the very outcome
this guard exists to prevent. Both spellings therefore look for the marker
token `SHIPWRIGHT_MIRRORED_MERGE_GATES`, which the real script declares in
its module docstring.

Three details in the PowerShell branch are load-bearing, because each is a
way the two spellings could stop agreeing about whether this step can STOP
the run:

- **The `Get-Command uv` precondition.** In bash a missing `uv` exits `127`
  and the `if` carries that status. PowerShell has no equivalent: a missing
  command raises `CommandNotFoundException`, which is *statement-terminating*
  — it abandons the rest of the `try` body, so a `$LASTEXITCODE` comparison
  placed after the call is **never reached**. Seeding that variable
  beforehand does not help either, in any value: the line that would read it
  does not run. Whether the un-caught error then produces a non-zero process
  exit depends on the host and on `$ErrorActionPreference`, which is exactly
  the ambiguity this step cannot afford. Asking whether `uv` exists *before*
  calling it is the one form that is deterministic.
- **`catch` re-raising.** It converts any other terminating error into the
  same explicit STOP, so the step's outcome never depends on the caller's
  error preference.
- **`try`/`finally` around `Pop-Location`.** The bash form uses a subshell,
  `( cd … && … )`, so the parent shell's directory is structurally unchanged
  whatever happens inside. `Push-Location` has no such guarantee: any
  terminating error between push and pop — including the throws above —
  would strand the shell in `{project_root}`, and every later F-phase command
  using a relative path would then resolve against the wrong directory.

Both spellings are given for the same reason `install-hooks.sh` has an
`install-hooks.ps1` beside it: a step that only runs under one shell is a
step that silently does not run for half the people who reach it, which
is the exact failure this whole phase was added to end.

The guard sits in the snippet, not only in the sentence beside it: the
script is repository-specific — it mirrors *its own* repo's workflow
steps by name — so where there is no such file the block must no-op
rather than fail for a reason that is not a defect. It runs from
`{project_root}` so `uv` resolves that project. In this monorepo the file
exists and covers `ci.yml`'s CI-gate guard plus the two surface
verifiers; `Repair-PR safety (gate)` is structurally un-mirrorable and
`Diff coverage (gate)` runs further down this same phase.

Then re-run the full suite NOW — do not rely on earlier results.

## Which command

**If the project declares a `suite` block in `shipwright_test_config.json`**
(this monorepo does), run the canonical suite runner:

```bash
uv run "{shared_root}/scripts/tools/run_test_suite.py" \
  --project-root "{project_root}" --run-id "{run_id}"
```

When `--run-id` is omitted, the runner generates one stable invocation id and prints it;
the same id is used by queue diagnostics, execution heartbeats, and any follow-up filed.

**Otherwise** (no `suite` block — the default for an adopted project), run the
project's own full-suite command as before, e.g.:

```bash
npx vitest run
npx tsc --noEmit

# Integration tests (if CRUD/DB changes)
npx vitest run --config vitest.integration.config.ts

# pgTAP tests (if new RLS migrations)
supabase test db
```

The runner is **opt-in**: with no `suite` block it refuses with an actionable
message and changes nothing for an existing project.

## What the runner does (and deliberately does not)

Since `iterate-2026-07-14-f0-parallel-suite`. The suite's units are already
isolated processes by design (ADR-044 namespace collision), so they are the
natural parallelisation unit — they were merely being run one after another
(measured: ~9.8 min serial, ~1.9 min now).

- **Units are DISCOVERED, not hardcoded** — the same selection rule as `ci.yml`
  (every `plugins/*/` with `pyproject.toml` + `tests/`, the three `shared/` test
  dirs, `integration-tests/`). A new plugin is picked up automatically; a
  hardcoded list would silently stop testing it. Guarded by
  `shared/scripts/tools/tests/test_f0_ci_parity.py`.
- **Units run the interpreter CI judges the push with** — every `uv run` the
  runner makes carries `--python`, pinned once in `suite_units.PYTHON_VERSION`
  and mirrored by a tracked `.python-version` at the repo root *and* in each
  plugin directory. Without the pin `uv` resolves per DIRECTORY from whatever
  the machine offers, and a plugin dir is its own uv project so the root file
  never reaches it: measured on `main` @ `6d2b2013`, F0 ran the 14 plugin units
  on 3.13.13/3.12.13 while every workflow ran 3.11.15 — F0 green, CI red, and
  the parity guard silent because it pinned unit *selection*, never the
  interpreter. Same guard now fails if the argv pin, a version file, or a
  workflow's `uv python install` disagrees (`iterate-2026-08-01-pin-python-311`).
  **Prerequisite:** the pinned interpreter must be obtainable. uv downloads it
  automatically, so this is invisible on a normal machine — but where downloads
  are blocked (`UV_PYTHON_DOWNLOADS=never`, offline, a managed proxy) F0 now
  fails *before* any test runs where it previously ran on an ambient 3.12/3.13.
  That is the intended trade — a gate on the wrong interpreter proves nothing —
  and the fix is `uv python install 3.11`. uv's own error is preserved in the
  runner's output rather than replaced by a generic failure.
  **First run in an existing tree rebuilds venvs.** Where a `.venv` was built on
  another interpreter, uv prints `Removed virtual environment at: .venv` and
  recreates it — measured, 1.4s for 23 packages. Anything hand-installed into
  those venvs is gone. The serial `warm_up()` only warms the shared uv cache and
  the ROOT venv, so the 14 plugin units each rebuild their own, concurrently, on
  that first run.
- **`pytest-xdist` is a per-unit OPT-IN** (`suite.xdist` allowlist), never a
  global `-n auto`. **`shipwright-compliance` is deliberately absent from the
  allowlist and must stay absent** — it is measurably NOT xdist-safe (5
  shared-state races in `test_test_evidence.py` under `-n 8`; the same tests
  pass 37/37 serially).
- **"Did pytest run?" is PROVEN, not guessed.** Each unit writes a JUnit report;
  the file exists iff pytest executed. This matters because `uv run` *also* exits
  `1` when it merely fails to build the environment — and sniffing its prose is
  unsound (pytest pluralises `error` → `errors`, so a fixture-level race that
  ERRORs every test reads nothing like a normal failure). `rc 1` + report = a real
  test failure; `rc 1` + no report = an infrastructure fault.
- **Serial re-verify (no false STOP).** A unit that reports a genuine pytest *test
  failure* is re-run **serially, without xdist, alone, after the pool drains**, in
  a clean temp dir — the way F0 used to run it. That verdict is authoritative.
  Red-in-parallel + green-alone does **not** stop the gate; the runner warns, and it
  is a race **or** a flaky test — the runner does not claim to know which.
- **…and the warning does not evaporate.** Since
  `iterate-2026-07-27-f0-race-triage` the runner **files the follow-up itself**
  (`shared/scripts/tools/suite_race_triage.py`), because "the unit must be triaged"
  addressed to whoever is reading the console is not a record — it dies with the
  session, and a race nobody wrote down returns when it is expensive.
  - One entry per unit in the **tracked** `.shipwright/triage.jsonl` of the run's
    project root: `source="f0-suite"`, `dedupKey="f0-race:<unit-id>"`, `severity=high`.
    F6 already stages that path, so it ships in the iterate PR and reaches `main`.
  - **Never auto-closed.** A race is intermittent, so one clean parallel run is not
    evidence it is gone; closing it on the next green run would recreate the very
    problem. An entry an operator already dismissed does not suppress a fresh one.
  - The card carries the **actual** commands the runner ran (the alone re-run and the
    whole parallel suite) and states that the cause is undetermined. It never carries
    captured test output — the tracked log is committed and published; the failing
    text stays in this run's console.
  - **Only the test-failure→green-alone class is filed.** A transient *infra* fault
    that did not reproduce is contention between concurrent `uv` processes, gets its
    own note, and is deliberately not tracked — filing that noise would bury the
    real signal.
  - **Exit 3 = a race was observed but could not be recorded.** An otherwise-GREEN
    run STOPs rather than passing with nothing written down. A run that is already
    RED keeps exit 1. The race itself still never stops the gate — only losing the
    record does.
- **An infra fault is retried once with the IDENTICAL command shape** (xdist still
  on). A *deterministic* fault (rc `5` nothing-collected, a usage error, an
  unprovisionable xdist) reproduces and still fails the gate — nothing is
  laundered. A *transient* one recovers: 18 concurrent `uv` processes create
  contention (hardlink races in the shared uv cache) that serial runs never had,
  and refusing those a retry would simply trade a race-induced false STOP for an
  infra-induced one. **The retry must never strip xdist** — that would green a
  suite that never ran the fan-out its config demands.
- **The diff-coverage gate CI runs, runs HERE too** (`iterate-2026-08-01-f0-diff-coverage-gate`).
  `Diff coverage (gate)` existed only in CI, so it could only fail *after* a push — 5
  of 22 sampled CI failures, landing after the iterate had already reported done. Each
  unit is now measured into its own `.cov-data/.coverage.<label>` file (its own, not a
  shared one: ci.yml runs the three `shared/` dirs serially and can `--cov-append` onto
  one target; F0 runs them concurrently and would be three writers racing),
  `combine_coverage.py` folds them into one repo-relative `coverage.xml`, and the pinned
  `uvx diff-cover@<version>` gates the **merge-base** diff at 80%. The version, the
  threshold and the command shape are asserted against
  `.github/actions/diff-coverage-gate/action.yml`'s own declared defaults, so F0 cannot
  drift into certifying a diff CI then rejects.
  **One flag differs on purpose — `--diff-file=<run-owned patch>` — and it is what
  makes the line sets coherent.** F0 runs *before* F6, so its final snapshot spans
  committed, staged, unstaged and untracked state. diff-cover's default union numbers
  those hunks against different file revisions; a dirty insertion above a committed
  hunk can therefore score the wrong lines. F0 instead creates a private temporary
  index at the merge base, stages the final working tree with `git add -A`, and passes
  that one patch. This includes untracked and excludes ignored files without touching
  the operator's real index or HEAD. CI needs no patch because its final snapshot is
  already one commit. Put disposable files under the repository's explicitly ignored
  `/.scratch/` directory; every other untracked source file intentionally participates.
  **The gate can be STRICTER than CI, and that is not a bug to route around:** a test
  that skips on your machine (no `bash`/`npm`/`docker`/`gh`, a platform guard) still
  runs in CI, so its lines can read as uncovered locally. The exit-4 message says so;
  the answer is to run the skipped layer, never to weaken a test or lower the threshold.
  **No workflow changed and the CI step stays** — it is the backstop for the three
  things a local run structurally cannot provide (a clean checkout, a pinned
  environment, a checker materialised from the PR's *base*). The local compare ref is
  therefore CI's declared `origin/main`, refreshed with the action's targeted
  `git fetch --no-tags origin main` and verified before diff-cover starts; a stale ref
  or differing `origin/HEAD` must not make F0 measure another line set. This is a **permanent**
  addition, not a transitional one. The measured conservative run is 6.7 min against
  a 1.9 min baseline; the cost was explicitly accepted after a warm diagnostic showed
  the existing 8-worker/C-tracer path is already the faster semantics-preserving
  setting. The trade is against the 1.18 extra CI cycles per branch observed at a 29%
  failure rate, which are a hanging PR plus a next-day re-entry rather than a longer run.
  **It fails closed**, with exactly one exception: when *no* unit had a measurable
  source root there is genuinely nothing to gate (`n/a`, green). A measurement that was
  attempted and did not arrive — a failed combine, a missing `coverage.xml`, `uvx` off
  PATH, an unresolvable compare branch — is exit `4` naming the phase, deliberately
  stricter than ci.yml's `hashFiles` guard, which cannot tell those two apart. Because
  the `uvx` launcher can also return `1`, that code is called "below threshold" only
  when diff-cover 10.3.0 also emitted its pinned threshold-failure signature. A
  checkout with `origin/main` but no merge base names `git fetch --deepen=100 origin
  main` as the repair.
  **A red suite skips the gate entirely**: coverage from a suite that did not finish is
  not a verdict, and the red units already STOP the run. It also skips the compare-ref
  fetch and private-index diff build, so a network/authentication problem cannot delay
  the authoritative red result. Green fetches are non-interactive and bounded to 120 s.
  Every gate-owned Git call uses `git -C <absolute-root>` and removes inherited
  `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, and `GIT_INDEX_FILE`; configure
  `origin` as the canonical remote CI uses. F0 executes repository tests and normal
  Git filters, so run it only in a trusted checkout.
  **One checkout, one F0 at a time:** an OS-backed lock spans reset → suite → combine
  → gate, so a second invocation exits `2` instead of deleting the first one's data.
  Its stable root rendezvous is outside resettable coverage state and survives reset.
  Combine and diff-cover use a unique invocation-owned XML until the verdict is known;
  only then is it atomically published as root `coverage.xml`, so another producer's
  fresh report can never certify this run.
  Before any authoritative retry, the failed attempt's base coverage file and exact
  pytest-cov/xdist suffix family are removed; only the accepted attempt is combined.
  Path plus bytes/symlink target of tracked and untracked, non-ignored `.py`/`.pyi`
  sources and test/coverage/interpreter/dependency config files are SHA-256
  fingerprinted before the suite, after suite/fetch/patch, and after diff-cover. If
  they change while F0 runs, exit `4` asks for a rerun; coverage and gated source
  therefore describe one snapshot.
  Every artefact is gitignored (`.cov-data/`, `.coverage*`, `coverage.xml`), so this
  never dirties the worktree the leak-guard is watching.
- The outer process pool and the inner xdist workers draw from **one** CPU budget
  (`cpu_count - 2`, or `suite.max_workers`). Across sibling worktrees, a weighted
  repository-keyed host lease caps the sum of those budgets at `cpu_count - 2`;
  compatible F0s may overlap, while exhausted capacity waits in FIFO order and names
  the blocking owner/run id. A separate exclusive host lease serializes uv preflight
  and warm-up, and is released before the CPU lease is requested. OS owner locks make
  process death release capacity; correctness never depends on deleting stale files.
  A hang is capped by `suite.timeout_seconds` (default 1800) and becomes a fault,
  not an infinite silent block.
- A repository should set `suite.max_workers` from measured **fleet** makespan and
  queue time, not from one run's latency. In this repository the measured request is
  11 on a 22-capacity host, allowing two sibling F0s to overlap. `integration-tests`
  is deliberately absent from `suite.xdist`: its tests already fan out subprocesses,
  and nesting xdist inside the outer fleet reproduced cache-ready deadline races.
- A dedicated parent thread continuously drains each attempt's combined stdout/stderr
  pipe into a fixed-size byte tail and publishes only that tail to the attempt-owned
  file. This bounds pipe pressure, memory, and disk simultaneously. The parent keeps
  deterministic UTF-8 replacement decoding,
  redacts known credential shapes, labels it `untrusted`, and atomically retains
  failure evidence under the canonical main repository's gitignored
  `.shipwright/runs/<run-id>/f0-diagnostics/`, resolved from linked worktrees so
  race-card evidence links survive worktree cleanup.
  JUnit existence remains the independent proof that pytest ran. On Windows the
  command is released only after its launcher is inside a kill-on-close Job Object;
  POSIX uses a process group. Timeout, cancellation, and normal return reap any
  remaining descendants before temp state and leases unwind.
- While units execute, the parent emits ASCII-safe queued/start/completion records plus
  a progress heartbeat with run id, completed/total units, and elapsed time. This keeps
  queued and long silent units observable but
  changes no pytest output, JUnit evidence, retry classification, or exit precedence.
  During an authoritative serial retry, `completed` counts units with a final verdict;
  `initial_completed` separately shows how many first attempts have returned.

> **Interrupted-run diagnosis may shard; F0 completion may not.** After a proven
> `KeyboardInterrupt` or lost runner channel, you MAY split only an affected pytest
> root into exhaustive, disjoint `test_*.py` file shards, with one pytest root per
> process and an explicit JUnit/exit result per shard. Use that evidence only to locate
> or diagnose the interruption. Shards never constitute F0 GREEN, even when every file
> passed; before F1, re-run the complete canonical `run_test_suite.py` command on the
> final working tree and require its zero exit.

> **F0 is an accelerated PRE-gate — be honest about it.** The retries remove false
> STOPs. They do *not* prove serial equivalence for units that *passed*: a test that
> passes only *because* of parallelism would not be caught here. That is why **CI
> stays serial** (`.github/workflows/ci.yml` is deliberately NOT parallelised) — CI
> is the authoritative serial gate before merge. This is not a convention but a
> **guard**: `test_f0_ci_parity.py::test_ci_stays_SERIAL` fails if `ci.yml` ever
> gains `-n auto` / `--numprocesses` / `pytest-xdist`. Do not "fix" CI by
> parallelising it, and do not claim F0's verdict is provably identical to a serial
> run.
>
> The retry gets a clean **temp dir** — but the repo **working tree is shared** by
> all units and is not reset. A unit reddened by another unit's tree pollution will
> reproduce on its retry and stop the gate. That is a known limit, not a claim.

## Read the actual output

- Exit code is 0 (`1` = a unit is red · `2` = suite config or host-resource
  coordination is unusable ·
  `3` = a race was observed and could **not** be recorded · `4` = the
  diff-coverage gate did not pass — add tests for the changed lines the report
  names, do not lower the threshold)
- Every unit `PASS` (a `RACE` warning is green — check it names a `trg-…` handle;
  the follow-up is already filed, so do not open a second one by hand)
- No type errors

If ANY unit fails: **STOP.** Go back to the build step and fix before
continuing. Do not proceed to F1 with failing tests.

→ Run /shipwright-preview to verify changes visually before committing.
