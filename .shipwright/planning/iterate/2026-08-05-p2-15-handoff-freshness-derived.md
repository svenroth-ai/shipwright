# Iterate Spec: P2.15 — the run's handover note survives its own finalization

- **Run ID:** iterate-2026-08-05-p2-15-handoff-freshness
- **Type:** bug
- **Complexity:** medium
- **Status:** complete
- **Card:** trg-01cd6aef (P2.15), supersedes trg-758e62c0

## Goal

Stop `restore_derived_to_head` from destroying the canon marker F5b writes into
`.shipwright/agent_docs/session_handoff.md`, so the two checks that ask "does this
note belong to this run" — F11's `check_session_handoff_fresh` and Canon **C3** —
stop reporting a true-but-self-inflicted staleness on every run whose branch fell
behind `origin/main`.

## Root cause (F-debug, four phases)

**Phase 1 — Read Error.** `session_handoff.md fresh` WARNs at F11 with
*"handoff was generated by `<previous run>`, not `<this run>` — re-run the F5b handoff
refresh so it describes this run"* (`verifiers/handoff_freshness.py:103`). Following that
remedy does not clear it: F5b already ran and its write is what went missing.

**Phase 2 — Reproduce.** Deterministic, 100%, no network — `scratchpad/repro_handoff.py`
(promoted to `shared/tests/test_handoff_survives_restore.py` in this change):

```
[after F5b]      ok=True   canon frontmatter names iterate-2026-08-05-this-run
[restore]        reset: ['.shipwright/agent_docs/session_handoff.md']
[preserve]       carries run_id='iterate-2026-07-28-previous-run'
[after restore]  ok=False  handoff was generated by iterate-2026-07-28-previous-run, not …
REPRO CONFIRMED
```

**Phase 3 — Recent changes.** Not a regression in either component; it is an
*interaction* created when `iterate-2026-07-27-derived-snapshots-off-branch` (#480,
`e21a7b71`) stopped iterates committing the handoff while `#459`/`#467` re-keyed the
freshness check onto the canon marker. Neither change is wrong on its own. Since #480
nothing has committed `session_handoff.md`: `origin/main`'s copy is frozen at `bebdc9a3`
(#493).

**Phase 4 — Boundary.** Good input becomes bad output at
`integrate_main.py:157` → `derived_snapshots.py:192` (`git checkout HEAD -- <handoff>`).
The restore's contract is "reset everything a producer can RE-DERIVE"
(`derived_snapshots.py:62`), and for this path that premise is false: the *body* is
re-derivable, but the **canon marker is run identity**, and no producer downstream of the
restore supplies it — F11's refresh runs `--preserve-canon-marker`, which faithfully
carries forward whatever is on disk, i.e. mainline's marker
(`canon_frontmatter.py:99`, "carries a marker of ANY age … unchanged").

**Root-cause statement (one sentence):** `restore_derived_to_head` resets
`session_handoff.md` to `HEAD` mid-run, discarding the run-identity marker F5b wrote,
because the path is classified as re-derivable when the only thing the reset destroys is
the one thing nothing downstream re-derives.

### Two corrections to the card, verified at code

1. **The card's stated deadlock does not exist.** "Satisfying the freshness check
   REQUIRES committing a file the derived gate forbids" is false: `read_handoff` reads the
   **worktree** file (`handoff_marker.py:104`) while `check_no_derived_snapshots_committed`
   reads the **commit's** changed paths (`derived_snapshot_gate.py:120`). A
   modified-but-unstaged handoff satisfies both. This is *not* the CI-supply-chain-ack
   shape (two ERRORs, `F6.md:99`).
2. **Frequency is "whenever the branch was behind at F11", not "every medium+ iterate".**
   `ensure_current` short-circuits `already-current` without integrating
   (`ensure_current.py:83`). Measured on the last 40 `origin/main` commits: median gap
   **0.90 h**, 69 % of gaps under 2 h — so behind-at-F11 is the common case, which is why
   it reads as "always".

### Why option (a) — "drop the freshness check" — was rejected

Measured, not argued (`scratchpad/repro_c3.py`): Canon **C3** reads the same bytes on
every Stop and fails identically after the restore —
*"the note is from an earlier iterate run … re-run this phase's C3 step"*. Dropping the
F11 check moves the noise onto a more frequent schedule and removes the only per-run
assertion that Resume depends on. The warning is a **true positive**; the fix is to stop
the damage.

### Why option (c) — "exempt it from DERIVED_SNAPSHOTS" — was rejected

It would let the handoff back into iterate commits, reinstating the N(N-1)/2 collision
class #480 removed, and it collides with P2.18's claimed file. This change keeps the
handoff in `DERIVED_SNAPSHOTS`, so `check_no_derived_snapshots_committed` still blocks it
from any commit.

## Acceptance Criteria

- [x] **AC1** `restore_derived_to_head` no longer resets a **modified**
      `.shipwright/agent_docs/session_handoff.md`; a **deleted** one is still restored
      (a deletion has no content to lose, and letting it ride would drop a tracked file).
- [x] **AC2** The run's handoff bytes are carried across the integrate merge by the
      existing `stash_run_written` / `unstash_run_written` pair, so a `git merge` cannot
      refuse on a tracked-and-dirty handoff.
- [x] **AC3** After a real `integrate_main` run against a mainline that moved the handoff,
      `check_session_handoff_fresh(project_root, run_id)` passes and Canon C3 for
      `phase=iterate` passes — both, from one integration test.
- [x] **AC4** `session_handoff.md` stays in `DERIVED_SNAPSHOTS`:
      `check_no_derived_snapshots_committed` still fails a commit that carries it.
- [x] **AC5** The registry pin `DERIVED_SNAPSHOTS - RESTORABLE_SNAPSHOTS` is updated to
      the new two-element set, and a forward drift assertion pins the new path constant
      into `DERIVED_MDS` (both directions, per the Registry-driven SSoT meta-test rule).
- [x] **AC6** `docs/hooks-and-pipeline.md` is updated in the same diff: the
      restore-exclusion paragraph ("Ten of the eleven") and the `session_handoff.md` row
      of the merge-reconciliation matrix.
- [x] **AC7** *(added after Stage-3 doubt review — the carve-out imports two new
      pipeline-stopping failure modes, and they must not ship unaddressed.)* Carrying is
      **best-effort for the note and terminal for the ledger**
      (`run_written_ledger.BEST_EFFORT_CARRY`): a note that cannot be taken off the
      worktree is reset to `HEAD` rather than left dirty for `git merge` to refuse on, and
      a note that cannot be written back is a step rather than the terminal
      `ledger_writeback_failed`. Both asymmetries are tested against the real failure.

## Out of Scope

- **The frozen committed copy on `main`.** Deliberate and already recorded:
  `compliance_refresh.py:97` classifies it `session_scoped` and `:132` lists it in
  `EXCLUDED` — *"per-session, meaningless on the default branch."* Not an open gap, so no
  follow-up card is filed (operator-confirmed, 2026-08-05).
- **Moving the handoff to a per-run path** (the card's option (b)) — a larger change to
  three readers for the same outcome; rejected at the approval gate.
- **`compliance_refresh.CLASSIFICATION`** — a *different* axis ("can the release refresh
  recompute this on `main`?"). `session_handoff.md` stays `session_scoped` there; the two
  taxonomies are deliberately not harmonised, and the diff says so where a future reader
  would be tempted.

## Affected Boundaries

| Producer (writes) | Consumer (reads) | Format |
|---|---|---|
| `finalize_iterate._generate_handoff` (F5b) | `verifiers/handoff_marker.read_handoff` (F11 + C3) | YAML canon frontmatter in `session_handoff.md` |
| `run_written_ledger.stash_run_written` | `run_written_ledger.unstash_run_written` | raw bytes, in memory across the merge |

The change does not alter either format — it changes *which* paths the second pair
carries. `touches_io_boundary` is not raised by the diff (no `.env*` / `*_config.json` /
`*_state.json` path, no new parse/dump call site), but the producer→file→consumer
round-trip is tested anyway because the defect lives exactly there.

## Confidence Calibration

- **Boundaries touched:** the two producer/consumer pairs above — F5b's canon marker read
  by F11 and Canon C3, and `stash_run_written` → `unstash_run_written` carrying raw bytes
  across the merge.

- **Empirical probes run:**
  - *Reproduction before any edit:* `restore_derived_to_head` on a repo whose `HEAD`
    carries a previous run's note → the F11 check flips from PASS to WARN with the exact
    reported message. 100% deterministic.
  - *Second reader:* the same restore → Canon C3 for `phase=iterate` fails with *"the
    note is from an earlier iterate run"*. This is what falsified the card's option (a).
  - *Frequency, measured not assumed:* last 40 `origin/main` commits → median gap
    **0.90 h**, 69% under 2 h, so "behind at F11" is the common case (the card said
    "every medium+ iterate"; the mechanism only fires when `ensure_current` integrates).
  - *Fix-dependence of every new test:* with the carve-out reverted, 8 of 11 turn red;
    with `BEST_EFFORT_CARRY` emptied, the 3 failure-mode tests turn red. The 3 that pass
    either way are labelled as guards in their own docstrings.
  - *The predicted failure, driven for real:* with `BEST_EFFORT_CARRY` empty and the
    stash's read forced to fail, integrate returns `merge_failed` carrying git's own
    *"Your local changes to the following files would be overwritten by merge:
    .shipwright/agent_docs/session_handoff.md"*. The doubt review's medium was a true
    positive, and the fix is verified against the real refusal rather than a mock.
  - *Registry reach:* `RUN_WRITTEN_SNAPSHOTS` is asserted to be exactly
    `DERIVED_SNAPSHOTS - RESTORABLE_SNAPSHOTS` and to contain the note, because the plan
    review could not tell from the plan alone whether the carve-out reached the stash.
