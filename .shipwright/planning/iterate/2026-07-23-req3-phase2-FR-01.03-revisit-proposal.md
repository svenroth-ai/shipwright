# FR-01.03 `/shipwright-plan` — revisit proposal (decide AFTER design)

Prepared overnight, 2026-07-23/24. **Nothing here is written into the catalog
yet** — the operator decides these after the `/shipwright-design` walk.

**Why a revisit.** FR-01.03 was walked against the Phase-1 module, before the
five fixes and three research-driven sharpenings. The corrected checklist adds
an **Outcome** dimension with a **fit criterion**, a **negative-space pass**, and
the **term-consistency** rule. Re-running FR-01.03 through it finds three real
gaps that the old checklist could not have surfaced.

## What survived unchanged

The nine current criteria all stand. FR-01.03 fared better on the outcome axis
than FR-01.02 did — several of its criteria are already properties of the
artifact (every requirement covered, every section traced back, sections carry
purpose/steps/test-strategy, numbering carries build order) rather than
descriptions of the phase's behaviour. The term-consistency check also passes
now: `section` is used throughout and is defined in the glossary.

## Gap A — a review's findings are counted, never addressed

**Verified.** `mark-review-state.py` writes `findings_count` as an integer.
Nothing in `review_marker.py` or `plan_compliance.py` checks the findings were
acted on — grep for `addressed|integrated|resolved` returns nothing.

So a plan can be reviewed by both models, raise twelve findings, ignore all
twelve, and still be recorded `completed` with `findings_count: 12`. The current
criteria cover only that a route was taken.

This is the same shape as the gap already found on the review route: the **fact**
of the review is recorded, its **effect** is not. Except this one is worse — the
route gap is caught later by the resume path and the compliance audit, whereas an
ignored finding is caught by nothing, ever.

> Proposed: *Given an outside review raised findings, when the plan is declared
> finished, then each finding has been either folded into the plan or recorded
> with the reason it was rejected — a review whose findings were only counted has
> not been done.*

Status if adopted: `prompt-only (mechanisable)`. The skill already instructs
"integrate findings, log every finding to decision_log.md", so this states an
existing promise; a count-versus-logged-decisions check is buildable.

## Gap B — "self-contained sections" is the headline property and is unstated

The row's own description promises the build phase can consume the plan **one
section at a time**. That property has no criterion. The nearest, "each section
says what it is for, lists at least two implementation steps, and states how it
will be tested", is a floor on *contents*, not the property itself: all three can
be present while the section is only intelligible after reading three others.

> Proposed: *Given a section, when someone builds it, then that section together
> with the prerequisites it names is enough to implement it — a builder does not
> have to read the other sections to know what to do.*

Fit criterion (what makes it answerable): the section names its prerequisites,
the files it expects to touch, and its test strategy. That is what a fresh
context actually needs, and it is checkable.

Status if adopted: `prompt-only (mechanisable)`. `check-sections.py` verifies
only that declared sections have files.

## Gap C — the end-to-end journeys for user-facing projects

`setup-planning-session.py` detects `e2e_exists`, but only to choose a resume
step. Nothing requires the plan to contain the journeys, and no criterion
mentions them. For a project with a user interface this is the artifact the test
phase later verifies against — its absence is silent.

> Proposed: *Given a project with a user interface, when the plan is finished,
> then it names the end-to-end journeys that must work, so the test phase has
> something to verify against.*

Status if adopted: `prompt-only (mechanisable)`.

## Questions for the operator — after design

1. **Gap A — should an unaddressed finding block the plan?** Recommended yes:
   a review whose findings are counted but ignored is theatre, and this is the
   one place with no downstream net. The weaker alternative is to promise only
   that findings are *recorded*, which is closer to today's behaviour but keeps
   review consequence-free.
2. **Gap C — is the journey list a promise for every user-facing project, or
   genuinely optional?** Recommended: promise it wherever there is a user
   interface. Today it is conditional on configuration, which means a UI project
   can reach the test phase with nothing to verify against.
3. **Gap B — is the proposed fit criterion the right bar?** Recommended as
   stated (prerequisites + files touched + test strategy). The risk of setting it
   higher is a section template nobody fills in honestly.
