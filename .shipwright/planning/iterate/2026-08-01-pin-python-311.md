# Iterate: the F0 gate runs the interpreter CI judges with

- **Run ID:** `iterate-2026-08-01-pin-python-311`
- **Intent:** BUG
- **Complexity:** medium (`prior_source: keyword`, no risk flags)
- **Spec Impact:** NONE — no FR gains, loses or changes behaviour. The F0 runner
  already runs the same *units* CI runs; this makes it run them on the same
  *interpreter*.

---

## Problem

`shared/scripts/tools/run_test_suite.py` is the F0 pre-gate: the thing that says
"this branch is safe to push". It spawns one `uv run` per test unit. None of
those invocations names an interpreter, and the repo tracks no `.python-version`
(`git ls-files .python-version` → 0 on every branch, never once in history).

So `uv` resolves an interpreter per unit, per directory, from whatever satisfies
`requires-python = ">=3.11"` on that machine. Every CI workflow that runs Python,
meanwhile, pins the interpreter explicitly with `uv python install 3.11` — five
of the seven; `codeql.yml` and `pr-review.yml` install no interpreter at all, so
there is no workflow anywhere that disagrees with 3.11.

Measured, `main` @ `6d2b2013`:

| Where | Interpreter |
|---|---|
| repo root `.venv` (main tree) | 3.11.15 |
| repo root, **fresh worktree** | **3.12.13** |
| 14 plugin venvs (main tree) | **3.13.13** |
| `plugins/shipwright-grade` (main tree) | **3.12.13** |
| every CI pytest process (9 runs sampled) | 3.11.15 |

The drift is not even stable across trees: the same repo root resolved 3.11.15
in one checkout and 3.12.13 in a fresh worktree, because resolution depends on
which interpreters happen to be present and what a `.venv` was first built with.

`test_f0_ci_parity.py` exists precisely to stop F0 and CI drifting apart. It
pins the *unit selection rule* and the *serialness*, and says nothing about the
interpreter — so the gate could certify a branch on 3.13 that CI then fails on
3.11, and every guard stayed green.

**Root cause, one sentence:** the F0 runner's `uv run` sites carry no `--python`
and the repo has no `.python-version`, so each unit's interpreter is resolved
once from ambient machine state **at environment-creation time and reused
thereafter**, instead of being pinned to the 3.11 that CI judges the push with.

The "and reused thereafter" is not pedantry — it is what the `pyvenv.cfg` files
say. The 13 plugin venvs point at a *system* `Python313`, `shipwright-grade` at a
*managed* 3.12, root at a *managed* 3.11: three different origins, each frozen
whenever that venv happened to be built. So the drift is sticky rather than
re-rolled per run, which is why it survived unnoticed and why the fix has to
invalidate existing venvs rather than merely influence the next resolution.
*(Sharpened after Stage-3 review, which measured the `home` values.)*

Not a regression. `--python` has been absent since the runner landed in
`0befc7d0` (#371, 2026-07-14) and `.python-version` was never tracked on any
branch — an original omission in a guard that was written to cover a different
axis.

## Correction to the brief that commissioned this run

The brief asked for exactly the change below, and the change is right. Its
stated *justification* is not, and the spec records that so the value of this
run is not overstated later.

**1. `run_test_suite.py` cannot cause a CI failure — CI never calls it.**
`grep -rn run_test_suite .github/workflows/` returns nothing. `ci.yml` carries
its own inline per-plugin and per-shared-dir loops. `build_command()` governs
the *local* F0 pre-gate only.

**2. No interpreter drift appeared in the CI sample.** Nine sampled CI failures
with pytest output (runs `30661869423`, `30623210476`, `30619403694`,
`30401492809`, `30401469586`, `30400218009`, `30356773896`, `30343722497`, plus
the shared-tests leg of the first) report `platform linux -- Python 3.11.15` and
nothing else. `uv python install 3.11` plus uv's managed-interpreter preference
already pins the five workflows that run Python.

*Scoped deliberately, after Stage-3 review:* that is evidence about **those nine
runs**, not a universal. One CI surface genuinely is unpinned —
`.github/actions/diff-coverage-gate/action.yml` runs `uvx diff-cover` with no
interpreter declared — and it appears in none of the nine. It is left unpinned by
decision, not oversight: `uvx` runs a pinned third-party tool whose own
interpreter never executes this repo's code, so it cannot produce the F0/CI split
this run is about. The new guard states that exemption in prose rather than
skipping it silently.

**3. "Run plugin tests" / "Run shared tests" is a step name, not a failure
class.** The sampled failures were seven unrelated logic and content bugs —
agent-doc entry budget (×2 runs), compliance delivery, silent-revert narrowings,
fold-map e2e, requirements-catalog contract, completion writers, gitleaks
extend. Nearly every test in the repo lives inside those two steps, so grouping
by step name approaches a tautology; 9-of-22 measures where tests live, not why
they broke.

**4. The prior-lore correction is itself tree-specific.** "The ROOT resolves
3.11.15" held for the main checkout and was false in a fresh worktree (3.12.13).

**What this run is actually worth:** F0 stops being a false pre-gate. A
3.11-only failure currently passes F0 and fails CI — the exact shape already
recorded in `conventions.md` for 2026-07-31 ("probe in the environment that
judges you"), where `pathlib` raises at construction on 3.11 and at first
derivation on 3.12+. It will **not** reduce the CI failure count the way the
brief predicts, because those failures were never interpreter-related.

## What was measured, so the design is not guessed

**A root `.python-version` does NOT reach the plugin units.** Probed in a clean
worktree: with `3.11` written at the repo root, `plugins/shipwright-adopt` (no
`.venv` yet) still built **3.12.13**. Each plugin carries its own
`pyproject.toml`, so it is its own uv project and version-file discovery stops
at that boundary rather than walking up to the repo root.

This is the fact that decides the design. The two halves of the fix are not
belt-and-braces; they cover disjoint ground:

| Fix | Covers |
|---|---|
| `--python 3.11` on the runner's argv | **all 18 F0 units** — argv beats every ambient source |
| root `.python-version` | every *other* bare root-level `uv run` (hooks, finalization tools, `uv sync`, manual dev commands) |

Unit cwd map, from `suite_units.discover_units`: 14 plugin units run in
`plugins/<name>` (own project → root file does not apply); the 3 shared units
and the integration unit run in `.` (root file applies).

**The re-resolve is not an infra fault.** The brief flagged a landmine: pinning
could trigger a re-resolve that surfaces as an F0 infra fault. Probed against a
root `.venv` already built at 3.12.13 — uv printed `Removed virtual environment
at: .venv`, rebuilt at 3.11.15 and installed 23 packages in 1.40s, exit 0. uv
handles the mismatch itself. The runner's junit-report-exists heuristic is
untouched by this change and stays the discriminator between an infra fault and
a test failure.

**Nothing in the repo needs >3.11.** All 15 `pyproject.toml` files declare
`requires-python = ">=3.11"` with no upper bound, and the tree's one interpreter
gate — `scripts/install.sh:46`, reading `sys.version_info.minor` — is a *floor*
(`>= 11`) that 3.11 satisfies. No ceiling exists to violate.
*(Corrected after Stage-1 review: an earlier draft claimed no `sys.version_info`
gate existed at all. The original probe grepped `--include=*.py` and could not
have seen a shell script. The conclusion is unchanged; the universal claim was
false.)*

## Acceptance Criteria

- **AC1 — every F0 unit runs on the interpreter CI pins.** `build_command()`
  emits `--python 3.11`, so all 18 discovered units (14 plugin + 3 shared + 1
  integration) execute on 3.11 regardless of ambient machine state or what a
  stale `.venv` was built with.
- **AC2 — the runner's other two `uv run` sites are pinned too.** `warm_up()`
  pre-builds the interpreter the units will actually use, and
  `ensure_xdist_available()` probes xdist on that same interpreter — a
  pre-flight that answers for a different interpreter than the units run is not
  a pre-flight.
- **AC3 — root-level `uv run` resolves 3.11.** A tracked root `.python-version`
  containing `3.11`, so hooks, finalization tools and manual dev commands stop
  depending on ambient state.
- **AC4 — the hand-run per-plugin command resolves 3.11 too.** Each of the 14
  plugin directories carries its own `.python-version`, because a root file
  cannot reach them (measured). `cd plugins/<name> && uv run pytest tests/` —
  the command `CLAUDE.md` documents — is a way to get a green light for code CI
  rejects, and it is closed here rather than left as a known gap.
  *(Operator decision, 2026-08-01: close it.)*
- **AC5 — the pin cannot silently rot.** The interpreter is asserted in both
  directions, and deleting either side fails: the runner's argv must carry the
  pin (`test_run_test_suite.py`, which owns argv assertions) and that pin must
  equal what every workflow's `uv python install` names (`test_f0_ci_parity.py`).
  Both files are the same F0 unit — `shared/scripts/tools/tests` — so they run
  together locally and in CI and cannot be satisfied separately. This closes the
  axis the parity guard was missing, which is what let the defect exist behind
  four green parity tests.
- **AC7 — the pin stays a monorepo fact and is never distributed.** The plugin
  `.python-version` files are excluded from every copy path in
  `update-marketplace.sh`, and the target-side prune paths deliberately do *not*
  exclude them, so a copy synced before this change gets cleaned out of an
  existing cache. **Why this is an AC and not a detail:** `update-marketplace.sh`
  copies plugin trees with a `find -type f` that includes dotfiles, and
  `shipwright-plan/skills/plan/SKILL.md` invokes `uv run --project {plugin_root}`
  at five sites. uv honours a version file in the `--project` directory —
  measured, 3.12.13 → 3.11.15 — so without this exclusion AC4 would silently
  force 3.11 onto **every end user** of the plugins, who agreed only to
  `>=3.11`, and would hard-fail them where interpreter downloads are blocked.
  The approval that authorised AC4 described it as affecting only a contributor
  testing one plugin by hand; this AC is what makes that description true.
  *(Surfaced by the Stage-3 doubt reviewer.)*
- **AC6 — the 15 version files cannot drift apart.** A guard asserts every
  tracked `.python-version` holds the same value as the runner's pin, so the
  duplication AC4 introduces cannot become fifteen disagreeing facts. The root
  file's *existence* is asserted, not merely its content: filtering absent files
  would leave AC3 as deletable as AC4 was before this run.
