## openai — verbatim

1. **dependency / high** — The plan creates `stamp_test_results.py` but does not identify or modify the actual test-result production path(s) that invoke it. A standalone stamping tool will not satisfy AC2 if CI, local test commands, alternate test layers, or failure/early-exit paths can write `shipwright_test_results.json` without subsequently invoking the tool. *Suggestion:* Locate every writer of `shipwright_test_results.json` and make stamping part of the authoritative write path (preferably immediately after the final result file is successfully written). Add integration tests that invoke the real production command/path, rather than only unit-testing the new tool.

2. **approach / high** — AC2's requirement that every existing top-level key be preserved "byte-for-byte" conflicts with the likely implementation of loading and reserializing JSON to add `source_state`. A normal `json.load()` / `json.dump()` will change whitespace, indentation, escaping, key ordering, trailing newline behavior, and potentially numeric representation throughout the file. *Suggestion:* Decide whether the requirement means semantic preservation or literal textual preservation. If literal preservation is required, use a narrowly scoped textual insertion/replacement strategy for the top-level `source_state` member, with tests against realistically formatted existing result files. If semantic preservation is sufficient, revise the AC to say so and use the existing project's canonical JSON serialization settings consistently.

3. **edge-case / high** — The "same work event" requirement is underspecified and may be temporally impossible depending on the existing lifecycle. The plan says compliance renderers resolve `run_id` from the work event that produced `Generated:`, but compliance documents are rendered at F5b while the described commit/event flow references F6/F7. If the relevant event is only recorded after rendering, a collector that selects the latest event could bind the document to a prior run. *Suggestion:* Identify the exact event-log record that is guaranteed to exist before each renderer runs. Resolve a single event object once — containing both its timestamp and run ID — and pass it into `ComplianceData`; do not resolve timestamp and run ID through independent "latest" queries. Add a test with multiple events, including a partially completed current run, proving the renderer selects the intended event.

4. **risk / medium** — The meaning and timing of `commit` and especially `dirty` for test results are not defined. If the stamp runs after tests generate or update result artifacts, `git status` may report the checkout dirty because of the results file itself, other generated evidence, or unrelated local files. That makes `dirty: true` noisy and potentially useless to the later validator. *Suggestion:* Define whether `dirty` means the full worktree state at stamp time, tracked source changes only, or source state excluding known generated artifacts. Resolve it in the actual repository root and document the exact Git command/pathspec behavior. Test clean, tracked-modified, untracked-only, generated-artifact-only, and no-Git cases.

5. **dependency / medium** — Adding a header line to five renderers is not sufficient by itself; all associated document fixtures, snapshots, expected generated artifacts, and any parsers or header-order assertions need review. The plan only names `audit_staleness.normalize()`, but consumers may assume `Generated:` is immediately followed by a blank line or a particular metadata/header shape. *Suggestion:* Search for each document name and `Generated:` across scripts and tests before implementation. Update golden fixtures and add a renderer-level assertion for each of the five documents that `Source-State:` appears exactly once immediately after `Generated:`.

6. **risk / medium** — The normalization change can accidentally weaken Group E comparisons if it removes arbitrary lines containing `Source-State:` rather than only the canonical generated header. It could also conceal substantive document content if a body line happens to begin with that string. *Suggestion:* Normalize only an exact, anchored header line in the expected banner position and only for the intended compliance document formats. Test that changing only `Generated:`/`Source-State:` does not produce staleness, while a changed body occurrence of `Source-State:` or any other content still does.

7. **edge-case / medium** — "Unresolvable" is described only at a high level. The approach needs behavior for a missing event log, malformed/latest event without a run ID, an empty or detached Git repository, Git executable failure, inaccessible repository root, and malformed pre-existing `source_state` JSON. Without this, the stamp tool could fail a test run or overwrite a corrupt record unexpectedly. *Suggestion:* Define a total resolution contract: `run_id`, `commit`, and `dirty` values for each unavailable source, whether failures are non-fatal, and whether malformed existing result JSON fails safely rather than being replaced. Cover no-Git/no-events and malformed-input round trips explicitly, as required by AC6/AC7.

8. **security / low** — Run IDs and event-log fields are being inserted into Markdown. If event logs can be influenced by branch names, commit messages, external input, or malformed records, an embedded newline could forge additional banner lines or alter the rendered document structure. Git invocation also becomes risky if repository paths or arguments are passed through a shell. *Suggestion:* Treat run IDs as a strict single-line token when parsing and rendering; reject or render unknown for values containing control characters/newlines. Invoke Git with argument arrays (`shell=False`), a fixed repository cwd, and bounded timeout/error handling.

9. **approach / low** — A new module is appropriate because two formats and multiple producers share a stable contract, but the plan should avoid turning it into a second source of event/Git resolution logic alongside existing staleness and compliance collectors. Duplicate "find latest run/event" implementations are likely to drift and directly undermine the stated "same event" guarantee. *Suggestion:* Keep `source_state.py` focused on the `SourceState` model, serialization/parsing, and a small resolution API. Reuse or extract the existing authoritative event-resolution helper rather than copying its scan rules; make the compliance collector call that same resolver once.

**Overall:** the design choice of a run ID primary stamp, with a test-result commit supplement, is sound and consistent with the stated lifecycle constraints. The main implementation risks are ensuring the stamp is wired into every real producer, defining snapshot timing precisely, and not violating the strict preservation requirement while editing existing JSON.

## gemini — verbatim

1. **Reducibility / Over-production — Medium** — Creating a dedicated `shared/scripts/tools/stamp_test_results.py` to post-process an existing JSON file introduces unnecessary I/O, risks race conditions, and makes AC2 ("byte-for-byte preservation of other keys") extremely difficult, as Python's standard `json.dump` often modifies whitespace, key ordering, or indentation. *Suggestion:* Avoid post-processing. Import the new `source_state.py` into the module that *already generates* `shipwright_test_results.json` and inject the `source_state` dictionary into the payload right before the initial `json.dump()`. If post-processing is strictly mandatory (e.g., the JSON is emitted by a third-party black-box tool), you must document the exact `indent` and `sort_keys` parameters required to prevent violating AC2.

2. **Risk — Medium** — AC5 mandates normalizing `Source-State:` exactly like `Generated:` during the staleness check. If `audit_staleness.normalize()` uses a regex applied to the whole file stream, blindly adding another line removal right next to it could break due to newline handling (e.g., `\r\n` vs `\n`), greedy modifiers, or consuming the blank line separating the header from the document body. *Suggestion:* Ensure the updated normalization regex test specifically covers edge cases for newline characters and guarantees it doesn't accidentally strip layout whitespace below the banner block.

3. **Edge Case — Medium** — AC7 handles degrading gracefully when a *run ID* cannot be resolved, but AC2 relies on system-level git commands to resolve `commit` and `dirty` state for test records. If tests run in an environment where `.git` is stripped or unavailable (like a downloaded release tarball or specific CI checkout configurations), the git sub-processes will raise exceptions and crash the build. *Suggestion:* Extend AC7's "degrade honestly" rule to Git. Ensure `source_state.py` catches `subprocess.CalledProcessError` or `FileNotFoundError` during git resolution, returning `null` for `commit` and `dirty` instead of failing.

4. **Edge Case — Low** — The spec doesn't define the idempotency of the stamping action. If an artifact generator or `stamp_test_results.py` is accidentally invoked twice on the same artifact, it might result in nested `source_state` JSON keys or multiple `Source-State:` Markdown banner lines. *Suggestion:* Add an explicit guard in both the JSON mutator and Markdown injection logic to quietly return (or overwrite) if the identifier already exists.

5. **Dependency — Low** — Injecting a new top-level key (`source_state`) into `shipwright_test_results.json` may break downstream schema validation if tools or CI pipelines validate this file strictly without allowing `additionalProperties`. *Suggestion:* Verify if a JSON schema file exists for the test results artifact in the repository and update it to allow the `source_state` object.

**Overall:** a thoughtfully constrained and highly logical spec that rightfully separates the *stamping* of the identifier from the *enforcement* of it. The primary risks lie in the mechanics of text/JSON mutation: streamline the JSON generation to avoid a fragile post-processing step, and ensure filesystem/git failures degrade as gracefully as missing event logs do.
