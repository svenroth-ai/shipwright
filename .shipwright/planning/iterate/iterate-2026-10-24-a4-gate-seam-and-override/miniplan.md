# Mini-plan A4: gate seam, rejection mechanics, v2 override (campaign brief-driven-run-a-real-gates)

Goal: BRIEF D4 step (2), acceptance A4. Put the phase validators (fixed in A3) behind an injectable seam in the driven (v2) apply path with enforcement OFF by default, define what a rejection is and what the master does with it, and give the v2 path a real override. A5 migrates the stub-artifact tests and flips the default.

Problem: in a driven run `single-session-apply` checks only result shape, artifact existence and `freeze_splits`; no phase validator runs (F18). The master has no handling for any apply rejection and nothing caps retries (`record_dispatch` only increments `attempt`). The only override is v1 `update-step --force --force-reason`.

Changes:
1. `validation_record.run_phase_gate(root, step, *, split_id=None, run_id=None)` forwards both to `validate_phase`. v1 `step_planning` keeps calling it positionally (None, None: unchanged). `record_validation_override` gains optional `phase_task_id` / `split_id` (written only when given) and a fourth `gate_result` value `degraded` (no ask issue, but a `kind: canon_degraded` note: the canon checks did not fully run, so it is not a `pass`). Schema enum + two optional properties.
2. New `orchestrator_pkg/phase_gate.py` (the seam): `ENFORCE_PHASE_GATE_DEFAULT = False`; `evaluate_gate(root, task, config, gate=None)` calls the injected gate or `run_phase_gate` with `split_id=task.splitId`, `run_id=config.get("runId")` (None when absent, never ""), turns a raising injected gate into a `[gate-error]` ask issue, and promotes every `canon_degraded` inform note to ask (a degraded canon run never reads as a pass on the v2 path). `retry_position(root, config, task_id)` reads `run_loop_state.json.attempt` (only when runId and currentPhaseTaskId match; else 0 = unknown). `terminal_for(config)`: `guided` (or absent) -> `ask_human`; any other autonomy (autonomous, future unattended) -> `failed`. `override_hook(...)` returns the `on_complete` callback that appends the override record.
3. `single_session/loop_state.py`: `MAX_GATE_RETRIES = 2`, `gate_retries_exhausted(attempt)` (attempt > MAX). Pure; the package still calls no mutator.
4. `apply_phase_result(..., override_reason=None, enforce_gate=None, gate=None)`. Order: mode guard -> contract -> task lookup -> (override: `normalise_override_reason`, refused `override_reason_required`; an ok=false result with an override is refused `override_requires_ok_result`) -> artifact guard -> **gate** (only when `result.ok and cas_current and task.status == "in_progress"` and (enforcing or override)) -> freeze_splits -> complete -> advance. Gate failure without override = non-mutating `{"ok": false, "reason": "phase_gate_failed", "issues", "inform", "checked", "attempt", "max_gate_retries", "retries_exhausted", "terminal"}`; task stays in_progress. When exhausted: guided -> `terminal: "ask_human"`, still non-mutating; autonomous -> `mark_phase_failed` (lifecycle, CAS) with the issue summary, loop pointer advanced like any strict-stop, `terminal: "failed"`, recoverable via `single-session-recover`. Gate pass under enforcement adds a `gate` block to the success payload. Enforcement off and no override: no gate call, payload byte-identical.
5. `phase_task_lifecycle.complete_phase_task(..., on_complete=None)`: called under `_PhaseTasksLock` after the task is marked done, before planning/write; the override record and the completion land in one write. Not called on the idempotent/CAS-reject branches, so a double apply never writes a second record. No new entrypoint (registry unchanged).
6. CLI: `single-session-apply --override-reason "<why>"` (default None; `""` reaches the library and is refused). `record_phase_end` also for a gate-terminal failure.
7. Docs: `single-session-loop.md` (rejection handling, issues[] brief, cap, terminals, override), run `SKILL.md` Step 5, `phase-runner.md` (`issues[]` input), `constitution.md` ASK FIRST, guide §7.5, `docs/hooks-and-pipeline.md` (loop diagram, override mechanism, gate_result values).

Alternative approach considered: run the gate report-only when enforcement is off (record findings, never reject) - rejected because the acceptance requires behaviour unchanged with enforcement off and the canon checks cost real time per apply.
Alternative approach considered: a separate `complete_phase_task_with_override` entrypoint - rejected: it would duplicate the CAS/done/plan body and add a registry entry; a hook keeps one completion path.

Tests (measured root `plugins/shipwright-run/tests`): new `test_single_session_gate_seam.py` (injected gate: off = unchanged, reject non-mutating, stale/double apply keep CAS/idempotent answers, retry cap + both terminals, degraded promotion, raising gate, run_id None vs config) and `test_single_session_gate_override.py` (reason required, record + completion in one write, idempotent re-apply writes no second record, ok=false refused, CLI flag, real project validator with planted transcript + bad grill trace rejected then passing when fixed, canon executed in apply path). `test_validation_override_record.py` / honesty additions for `degraded`, `split_id` forwarding, loop_state cap.
Risks: `gate_result: degraded` is new on v1 too (only reachable when canon was degraded, i.e. since A3). Attempt counts every dispatch of the task, including crash-resume re-dispatches.
