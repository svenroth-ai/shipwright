# Architecture Brief: decision-log-drops-index

## The problem

An agent that needs to check prior architectural decisions has two large
sources to read in full: a single log file with hundreds of entries, and a
staging directory of pending entries not yet folded into it. Reading either in
full costs tens of thousands of tokens even when only a handful of entries are
relevant, so in practice both go unread and prior decisions get silently
re-litigated or contradicted.

## What already exists here

- A spec-document folder in this project already has a generated
  table-of-contents file, kept in sync with its own source whenever that
  source changes, and checked for freshness in CI.
- The two sources in question — the single log file and the staging
  directory — currently have no such table of contents.

## What would newly, permanently exist

Two small generated index files, one per source, each regenerated by the
existing code paths that already write to that source (no new trigger, no new
job). One of the two indexes becomes a tracked, committed file with a CI
freshness check; the other stays local-only because its source directory is
itself never committed. Whoever changes either source from now on is already
running the code that keeps its index current — no separate maintenance
burden is created.

## Options on the table

- **A:** Generate a table-of-contents for each source, refreshed by its
  existing writers, mirroring the pattern already used for the spec-document
  folder.
- **B:** Leave both sources as full files/directories and rely on agents
  reading them in full when needed.
- **C:** Build a single unified query/filter layer over both sources (and any
  future ones), rather than a plain table of contents for each.

## Constraints that are not negotiable

none
