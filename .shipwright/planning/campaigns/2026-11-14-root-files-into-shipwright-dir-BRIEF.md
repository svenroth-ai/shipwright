## 4. Review findings that change the design (all verified in the repo unless noted)
### 4.1 Silent-failure traps (must be closed before any move)
- **Mandatory-review list goes blind.** `plugins/shipwright-security/scripts/tools/review_record_tier.py` (`SENSITIVE_PATH_RE`, anchored `^`, lines ~71/74) names `shipwright_accepted_risks.yaml` and `shipwright_bloat_baseline.json` as root paths. After the move a PR editing the risk register or baseline would no longer count as "sensitive". R1: match both locations (+ add `inline_suppressions`), with a test.
- **Change-type sorter.** `shared/scripts/lib/change_type_paths.py` classes `.shipwright/**` as bookkeeping, ahead of root globs `shipwright_*.json|yaml` (tooling/infra/compliance). Add `.shipwright/config/shipwright_*` to those sets before the bookkeeping rule; R0a must survey globs/regexes/fnmatch, not just literals. (`risk_detectors.py` is basename-based and keeps working.)
- **Bloat gate fails OPEN.** `bloat-check.yml` (line ~84-86) falls back to an empty baseline when `git show <base>:shipwright_bloat_baseline.json` fails; `anti_ratchet.load_baseline_override` returns None ("fail-open"); `scripts/hooks/pre-commit` line 31 skips the whole check when the root file is absent. Moving the file before all three readers are updated gives a green gate that checked nothing. R1 updates all three to read both locations AND makes "baseline missing in both places" a hard failure in this repo, with a CI test that fails when the anti-ratchet runs with no baseline loaded. (This corrects the earlier brief, which said the PR "fails its own gate".)
- **`.gitignore` is two problems, not one.** (a) The managed block ignores `/.shipwright/*`; needs `!/.shipwright/config/` or tracked files drop out of git silently. (b) The root `.gitignore` has an UNANCHORED `shipwright_*_config.json` (line 79) whose exceptions are root-only (`!/shipwright_*_config.json`); inside `.shipwright/config/` it still ignores NEW config files (moved ones stay tracked, new ones — fresh worktree, sync/model/design/deploy config — are skipped by `git add`). Fix: `!/.shipwright/config/shipwright_*` after every basename rule, and the self-heal must detect basename rules. Test: `git check-ignore --no-index` on every moved path in this repo and in a temp repo using the canonical template.
- **Derived and temp files become add-able.** The consumer template `shared/templates/shipwright-gitignore.template` has no `*.json.lock`/`*.tmp` rule (only this repo's own `.gitignore` does), and a folder-level re-include would expose `shipwright_test_results.json` (derived, never staged). Add `/.shipwright/config/*.lock`, `*.tmp`, and decide explicitly whether `test_results` is ignored in consumers.
- **The migration tool checks the ignore rules first:** it refuses to move unless `git check-ignore` confirms the new paths are NOT ignored (precondition, like the events heal probe).
- **Consumer CLAUDE.md `@imports`.** `shared/templates/claude-md-template.md` lines 73-78 load the configs via `@shipwright_run_config.json` etc.; Claude Code drops a missing import without a warning, so a migrated repo silently loses its context. The template flips in R3; the migration tool finds and rewrites `@shipwright_*` lines in CLAUDE.md / AGENTS.md (human-owned: dry-run report and explicit consent), and `session-handoff.md.template` / `codex-agents-md-appendix.md` are covered.

### 4.2 Old plugin meets new layout (the dangerous direction)
Root-finding walks up looking for `shipwright_run_config.json` (`check_required_checks_hook.py`, `track_tool_calls.py`, `session_start_using_shipwright.py`, `suggest_iterate.py`, `aggregate_triage_on_stop.py`). On a migrated repo an OLD plugin (other machine, stale cache, teammate) finds nothing, concludes "not a Shipwright project" and switches every hook/gate off — or falls back to defaults. Mitigations (to decide, section 8): a tiny root pointer file through R4 (`{"moved_to": ".shipwright/config/", "min_plugin_version": X}`) that new code ignores and old code still recognises as a project; and an ordering rule: **every outside reader (WebUI, CI templates, hook, plugin cache) must ship read-both-places BEFORE any repo migrates.** The migration tool may check the installed plugin version.

### 4.3 Transition rules must be explicit (state table)
R1 "read both", R2 "hard abort on old file" and R3 "writers flip" contradict each other if the abort ships before the flip (it would fire in every repo, since writers still write the root). Decision: **the hard abort ships WITH the flip (R3), as in the events precedent**; before that, "both copies exist" is a loud error, never a silent preference for the new copy (divergent copies are reported with a migration instruction; byte-identical ones accepted). R1 gets a release-by-release table (release → reader mode, writer mode, abort on/off) so no release has both behaviours live.
R0b must not change behaviour: it resolves to the OLD root location, only centralised.

### 4.4 Locks
Decide in R0b, before any data moves: ONE lock path independent of where the data file lives, used by every writer from R1 on. Reviewers split on where (GPT: next to the data, GLM/plan reviewer: `.shipwright/locks/`, already ignored by `**/.shipwright/locks/`, solves the template gap). **Recommendation: `.shipwright/locks/`** (it is already the project's lock home and ignored; this contradicts "everything in config" only for lock files, which are not config). Locks and `.tmp` are excluded from content-dedup in the migration tool; during the skew window lock exclusion between old and new plugins is advisory only (documented); `generate_handoff_on_stop.py` relies on the shared run_config lock.

### 4.5 Campaign mechanics
- Campaign PRs edit the same files each wave; **no campaign may run when R3 merges** (drain first). Correction: a branch editing the old path usually resolves through git rename detection after a `git mv`; the real hazard is old code writing the root path again after the merge (caught by the hard abort). Also **standalone iterate worktrees and unmerged branches** (many under `.worktrees/`) are not covered by "drain campaigns": R3 pre-flight lists every open worktree/remote branch touching a moved file (`git for-each-ref` + `git diff --name-only origin/main...<b>`) and each must be merged, rebased or migrated first.

Make the resolver record each file's KIND (config, baseline, register, derived) so these lists are generated from it.

### 4.7 Round-2 corrections (second review round, 2026-11-20) — these OVERRIDE earlier wording where they conflict
1. **The root pointer is its own kind, with a defined shape.** Old code detects a project by the literal root name `shipwright_run_config.json`, and old loaders (`lib/config.read_config`, `phase_quality/_engagement.py:138`, `_resolution.py:166`, `required_checks_state.py:77`) parse it as a REAL config: they get defaults or "not engaged" instead of an error, the exact silent failure we want to avoid. R0a builds a table of how every old reader behaves on (missing file / pointer content) and the pointer's format is chosen FROM that table (content old loaders cannot misread, so they hit their None/"engaged" branches). The pointer carries a content signature (e.g. `"$shipwright_pointer": 1`); the resolver, the R1 both-copies check, the R3 hard abort and the migration tool all exempt it BY that signature, and a test covers the dangerous case: a non-pointer root copy next to a migrated copy must still abort. The migration tool's plugin-version gate is the PRIMARY defence, the pointer secondary. Decision 8.3 becomes per-file rows in the R1 state table (a separate row for the release in which `run_config` moves).
   Correction to 4.2: `track_tool_calls.py`, `check_required_checks_hook.py` and `aggregate_triage_on_stop.py` use `is_shipwright_project` (`project_root.py:36-50`), which also accepts the root `shipwright_events.jsonl` that stays, so they do NOT switch off. 2. **Locks: dual-lock, not "advisory".** Old writers keep taking the root `<name>.lock` (`run_config_store.py:62`, `generate_handoff_on_stop.py:71`, `append_phase_history.py:199`, `append_iterate_entry.py:324`, `brief_dir_intake.py:217`, `backfill_phase_tasks.py:83`, `mint_ac_ids.py:131` for the registry). From R1 to R4 every upgraded writer takes BOTH locks in a fixed order (legacy root lock first, then `.shipwright/locks/<name>.lock`), encapsulated in `shipwright_paths.lock_for(kind)` so no caller builds a lock path itself; the legacy lock is dropped in R4. R0b's `lock_for()` returns the current root names (no behaviour change); the dual-lock starts in R1. R2 ships the tool and docs; real runs happen only at the writer flip (R3) and require a per-repo gate: its active readers and writers (CI, WebUI, teammates, cached plugins) are on the dual-read version, and writes are stopped during the move. Document supported reader/writer combinations and recovery from an interrupted move.
4. **`--reverse` is conditional:** it refuses (or needs an explicit flag plus documented plugin downgrade) when the installed plugin is at or past the flip release, otherwise the post-flip hard abort fires on the root file the rollback just created.
5. **Constructed names and derived lock paths are survey classes.** The R0b guard must also catch f-strings and concatenations: `plugins/shipwright-compliance/scripts/audit/group_a.py:340` (`f"shipwright_{config_name}.json"`; when the file is missing the A4 audit returns "skip" at :310-311, so it must report fail/unverifiable once a config is missing at both places), `shared/scripts/tools/generate_session_handoff.py:430` (tells the next session to read a root path), `X_NAME + ".lock"`, `.with_suffix(".json.lock")`. 6. **Derived snapshot blind spot:** `derived_snapshots.py:224` runs `git status --porcelain -- <DERIVED_SNAPSHOTS>`; after the flip an old shipwright-test plugin writing the ROOT `shipwright_test_results.json` would be swept in by `git add -A` and no longer seen. Keep BOTH paths (legacy and new) in `DERIVED_SNAPSHOTS` until R4 (the resolver emits both for kind=derived) and include `shipwright_test_results.json` in the R3 hard-abort/diagnostic set.

**Decision for the pointer (replaces the example in 4.7.1):** use shape **D, a short non-JSON text stub**, not a JSON object or array.
- Why: every old WRITER refuses it loudly (`ValueError`, `IterateAppendError`, `BriefRefused`, `JSONDecodeError`, `RunConfigUnreadable`) and leaves it untouched; every old TOLERANT reader degrades through the branch it already has for a corrupt file (`cfg is None` means engaged, `{}`, inert mode); every marker test still passes (existence only), so hooks and gates stay on. Shape B is read as a real, empty config by 33 guarded readers and is silently written INTO by `append_phase_history` (measured above) and by the WebUI. Shape C crashes `master_stop_check` (the Stop hook) and `setup_implementation_session`-style readers and still lets the tolerant `_load_config` overwrite the stub on the next save.
- Format (ASCII, one line of signature, then plain text, 512 bytes at most, LF endings, no BOM, no trailing JSON):
```
SHIPWRIGHT-POINTER/1
moved_to: .shipwright/config/
min_plugin_version: <version of the flip release>
This file is a stub left so older Shipwright plugins still recognise this project. Shipwright now keeps its configuration in .shipwright/config/. Update the Shipwright plugins; do not edit or delete this file.
```
- The signature is the exact first line `SHIPWRIGHT-POINTER/1` followed by LF; new code (resolver, the R1 both-copies check, the R3 hard abort, the migration tool) exempts a root `shipwright_run_config.json` BY that line plus the size cap and nothing else, and the 4.7.1 test still applies: a root file without the signature next to a migrated copy must abort. A non-signature root file of any other shape is a real config.
- Side effects to accept and document: (a) editors, `jq` and any JSON linter flag the file as invalid (that is the loud failure, and the text says why); (b) the orchestrator's tolerant path prints "Delete the file and re-run /shipwright-run to recreate"; an operator who follows it deletes the stub and falls back to state A (a Shipwright-blind old plugin), which is the case the plugin-version gate (4.7.1, primary defence) already covers; (c) `lib.config.read_config("run")` and `phase_task_core._read_config` raise `JSONDecodeError` instead of returning `{}`: they raise only for a run that is already past the flip with an old plugin, and a raise is the right outcome there; (d) the new-code CI step that validates `*.json` (if a consumer has one) must exempt the stub by signature.
- Only `shipwright_run_config.json` gets a stub (decision 8.3, it moves last and is the marker). No other moved file gets one: their missing-file behaviour above is the real exposure and is handled by the R1 dual-read plus the plugin-version gate, not by stubs.
