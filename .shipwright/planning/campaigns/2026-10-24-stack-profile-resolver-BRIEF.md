## 0. Why

A stack profile is a JSON file `shared/profiles/<name>.json` (bundled: `supabase-nextjs`, `vite-hono`, `python-plugin-monorepo`). Projects store only the profile NAME (`shipwright_run_config.json.profile`, schema: free string/null). The file is resolved from the installed plugin tree, and an update replaces that tree, so a profile a user wrote there is lost on the next update. Goal: write a profile once, in the project or the home directory, and every Shipwright phase finds it.

## 1. Design decisions (binding for all units)

**D1 Lookup, first FILE wins, no fall-through:** `<project>/.shipwright/profiles/<name>.json` -> `~/.shipwright/profiles/<name>.json` -> bundled. If the winning file is unreadable, not JSON, or fails validation, resolution FAILS naming the file; it never continues to a lower source or another profile. Not found anywhere (and not a reserved sentinel) fails, listing the searched paths. Shadowing a bundled name is allowed (copy-and-edit flow) and reported as `shadows: <path>`. **Discovery is not selection:** `list`, the adopt matcher and S6 may skip an invalid candidate with a `warnings[]` entry (it keeps ownership of its name, so a lower source with that name is not offered instead); a run-config profile or an explicit override MUST fail.
**D2 One implementation, complete API, defined import mechanics.** Module `shared/scripts/profile_resolver.py` (top-level next to `markdown_table.py`, not under `lib/`: plugins own a `lib` package of their own and `import lib.x` binds the wrong one, ADR-044/045). Stdlib-only; at module scope only `os.path`/constants (no `Path.home()`, no platform-gated imports, no pathlib arithmetic - the dev_server import pins above). API, all pinned by S1 tests: `search_dirs(project_root)` (the D1 triple), `resolve_profile(name, project_root, *, search_dirs=None)`, `list_profiles(project_root, *, search_dirs=None)`, `load_profile_file(path, expected_name=None)` (parse + D5 validation, for `--profile-path` / `--profile-dir` / explicit dirs; **returns the same `ResolvedProfile`, classifying the path against `search_dirs()`**: inside a source dir -> that source and its `shadows`; an unrelated path -> `source: explicit`, treated as custom for D8/D9, so a custom file named `supabase-nextjs` passed via `--profile-path` never receives bundled-only defaults or skips the shadow warning), `validate_profile_data(data, path)`. Errors `ProfileNotFound` / `ProfileInvalid` / `ProfileSchemaDrift` subclass `ValueError` and carry `.kind` and `.exit_code`, so no caller depends on class identity across import paths. **Import convention (existing repo practice, no new loader helper):** the module has a unique top-level name, so every consumer appends `shared/scripts` to `sys.path` (APPEND, never `insert(0)`; see `accepted_risk_view.py:81-85`, `from markdown_table import ...`) and does `from profile_resolver import ...`; `validate_env.py` (also imported as `shared.scripts.validate_env`) does the same, so one module object results. Callers catch `ValueError` and branch on `.kind`; no caller names the exception classes. A boundary probe (zero internal imports) per consumer test root proves the import works through the plugin's real layout. **Hot-file rule:** only S1 edits `profile_resolver.py`. A resolver gap found in W1+ STOPS that unit (released, replanned); it is never worked around at the call site.
**D3 Names:** `^[a-z0-9][a-z0-9-]*$`, all lowercase (an upper-case file name is an error, so Windows/macOS and Linux behave the same). Reserved, compared case-insensitively: `generic`, `detecting`, and the Windows device names (`con prn aux nul com1-9 lpt1-9`); a file with a reserved name in any source is an error. Containment: resolve the candidate once with `Path.resolve()`, require `is_relative_to(<source dir resolved>)` (covers symlinks and junctions), and read through that resolved path. Name rules apply to name lookups only; explicit file/dir flags skip D3 but still get D5. Named resolution also checks the actual directory-entry spelling (list the directory, compare exactly), so `Vite-Hono.json` is a deterministic error on Windows, macOS and Linux alike, and two entries differing only in case are an error.
**D4 Test isolation:** user dir = `SHIPWRIGHT_USER_PROFILES_DIR` if set, else `Path.home()/".shipwright"/"profiles"`. The repo-root `conftest.py` does NOT load for plugin roots (each plugin has its own pytest config; CI runs `cd plugins/<name> && pytest tests/`; the root file is deliberately fixture-free). So S1 puts the autouse fixture in ONE shared helper module and imports it from the `tests/conftest.py` of every root that touches profiles: `shared/tests`, `shared/scripts/tests`, `shared/scripts/tools/tests`, `integration-tests`, and the plugins `shipwright-test`, `shipwright-adopt`, `shipwright-design`, `shipwright-project`, `shipwright-run` (env is inherited by subprocesses). A canary test in one plugin root asserts the variable points into a tmp dir. A missing, unreadable, or non-directory user dir is "absent" for `resolve`, and a `warnings[]` entry in `list`.
**D5 Schema (minimal):** `shared/schemas/stack_profile.schema.json`, `additionalProperties: true` everywhere except where a wrong type would crash or misroute a command. Required: `name` (== file stem for name lookups). Optional integer `schema_version` (absent = 1; decided to keep: the card requires a clear failure after an update, and one integer compare is cheap). Typed keys: `services[]` (`name`, `command`, `port` as integer **or** placeholder string such as `"${PORT:-3847}"`, `ready_path`, `depends_on`, `primary`), `dev_server` (object or null; read at `profile_config.py:219,238`), `testing.unit` (string **or** object - polymorphic today), `testing.command` (string), `testing.integration|e2e|db_tests` (object or string), `testing.performance` (read at `performance_check.py:684`), `required_env_vars`, `rules`, `folder_structure`, `migrations`, `design_system`. `stack.*` is untyped (bundled profiles carry a string `_comment` inside `stack`). Keys starting with `_` are comments, allowed anywhere. `version` (the profile's own string version) is documentation-only and must not be confused with `schema_version`. Everything else documentation-only. **Validator:** the resolver implements a small schema-driven checker for exactly the constructs the schema file uses and REJECTS an unsupported construct loudly (so the schema file and the enforcement cannot silently diverge). A CI test in the shared test root (where `jsonschema` exists) asserts the hand checker and `Draft202012Validator` agree on the three bundled profiles plus a set of mutation fixtures. Drift = unsupported `schema_version`, or a typed key of the wrong type; the message names the file, the problem, the version this Shipwright supports, and "copy the bundled profile `<closest>` as a new starting point".
**D6 Registry tests (forward direction only):** each loader declares the profile keys it consumes in a module-level constant; a test asserts every declared key exists in the schema. `shared/profiles/*.json` is either a stack profile or listed in the resolver's `NON_PROFILE_FILES` (both directions, three entries). No "every schema key has a reader" reverse check.
**D7 CLI** `shared/scripts/tools/resolve_profile.py` (PEP 723 header; prose invokes it with `uv run --no-project` so a broken target-project `pyproject.toml` cannot block resolution): subcommands `resolve`, `list`, `validate`; flags `--project-root`, `--name`, `--json`, `--path-only`. Exit codes: 0 ok, 2 not found, 3 invalid/drift, 4 usage (override `ArgumentParser.error` so argparse's own exit 2 does not collide). **stdout carries only the requested output; the "source/shadows" provenance goes to stderr** (loaders that print JSON for skills to parse must not get an extra stdout line; they put `profile_source` inside their JSON). `resolve --path-only` for a reserved sentinel prints nothing and exits 0; every prose snippet states the branch "empty path = built-in defaults". stdout/stderr are reconfigured to UTF-8 (Windows cp1252 consoles, non-ASCII home paths). `list --json` carries `contract_version: 1` (WebUI consumer, cross-repo): a pinned fixture test, and any change to its shape is a major bump. `list` and `validate` are strictly read-only: no subprocess, no `_expand_env` (test asserts this).
**D8 Trust.** A project-level profile can carry commands that run: `test_runner.run_tests` uses `shell=True`; dev_server `services[].command` uses `shlex.split` + `Popen` with a list (`spawn.py:83-87`, no shell) but is still arbitrary process execution, and `_expand_env` expands environment variables into commands. Same trust class as the repo's own `package.json` scripts / `conftest.py` that `/shipwright-test` already runs, so no separate approval gate (decided by reviewers, internal + GPT; confirmed no hook runs profile commands without a phase being invoked, `shipwright-grade` reads no profiles). Conditions: (a) every resolution that precedes a command run emits the source line (stderr); (b) **a project- or user-level profile that shadows a bundled name emits a distinct, prominent warning at every loader resolution, not only in the CLI** (the real residual risk is a repo silently replacing `vite-hono`); (c) adopt marks a project-sourced match as such in its result; (d) S2 traces each command-executing call site and confirms it runs only after a phase the user invoked; (e) the decision is recorded as a decision-drop, which also names two accepted residuals explicitly: `~/.shipwright/profiles/` commands run in EVERY project including untrusted clones, and `_expand_env` substitutes project-controlled environment variables into those commands (attacker precondition: the user has such a profile AND opens a hostile repo AND runs a phase; existing control: the same repo's own scripts already run in that phase).
**D8f Provenance reaches the command-running loader.** Prose for the test layers does NOT hand a bare path to `--profile-path`: it passes the profile NAME and project root (`test_runner.py --profile {profile} --cwd {project_root}`; `performance_check.py` gains optional `--profile`/`--project-root`, `--profile-path` stays for explicit files) so the loader resolves natively and knows the source. `--path-only` remains for read-only prose sites. The `load_profile_file` source classification (D2) is the backstop for explicit paths. A D9 regression test runs through the prose-shaped invocation.
**D9 Provenance, not names, selects bundled-only behaviour.** `PROFILE_TEST_COMMANDS`, `DEFAULT_COMMANDS`, CI/CodeQL templates and any other name-keyed default apply only when the resolved source is `bundled` (or `builtin` for the generic defaults), never to a custom profile that happens to carry a bundled name. Regression test: a project profile named `supabase-nextjs` with its own commands gets its own commands and no bundled template.
**D10 Project profiles must be committable.** S1 adds `!/.shipwright/profiles/` to `shared/templates/shipwright-gitignore.template`, the repo's managed `.gitignore` block, and updates the template drift test (the adopted-project gitignore self-heal picks the new line up). `CLAUDE.md` "Where documents live" says `.shipwright/` is never hand-composed: S5 amends that sentence to name `.shipwright/profiles/` as the one hand-authored exception.

### S3 - Adopt, matcher, scaffolds, run-config
1. `match_profile` takes an ordered list of directories; custom profiles score by the same rule (>= 0.30 else `generic`); first directory owns a name (D1); discovery skips an invalid candidate with `warnings[]` (D1); a project-sourced match is marked `source: project` (D8c).
