## 1. Design decisions (binding for all units)

**D1 Brief package.** SPEC §5: `brief.json` v2 (`profile`, `deploy_target`, `autonomy`, `ui_host`, `ux_shape`, `source_class`, `scope`, `design_system`, `brief_dir`, `env_preflight`, `allow_parallel_builders`, `approved_by`, `approved_at`, `package_sha256`), `brief.md`, `scope.md`, `screen-map.json`, `chat-map.json` (chat-first only), `mockups/`, `visual-guidelines.md`, optional `inputs/`; `evidence/` never committed, never read by a phase.
- **Location:** `brief_dir` is project-relative and committable; the default is `<project>/brief/` (NOT under `.shipwright/`, which is gitignored and would break resume from worktrees and CI).
- **Hash:** one implementation in `shared/scripts/lib/brief_package.py` (created and tested in A1; B and U import it, nobody re-implements it). It hashes a **manifest**: POSIX relative paths, NFC, sorted, one SHA-256 per file; text files are normalised CRLF→LF before hashing; `evidence/`, symlinks and OS junk are excluded; `brief.json` is hashed as canonical JSON **minus** `package_sha256`, `approved_by`, `approved_at` (so consent fields such as `autonomy`, `allow_parallel_builders`, `deploy_target` ARE protected). A hash proves the package is **unchanged since approval**, not that a person approved it; any agent can recompute it. Verification points (owned by B2 for write-config, resume and answers; U3 for design-gate resolution): before `write-config`, on every resume and every `needs_input` answer, and when a design gate is resolved. Any mismatch invalidates the approval and escalates.
- **Fixture approval:** fixtures carry `approved_by: "fixture:<id>"`. Preflight accepts that **only** when the operator sets `SHIPWRIGHT_ACCEPT_FIXTURE_APPROVAL=1`; the acceptance is recorded in the report and `run_config`; otherwise it is refused like any missing approval.
**D2 Intake.** The package is read from a directory; `brief_dir` persisted in `run_config` so resume finds it. The `--brief` file route keeps its behaviour (adopt shares `brief_intake`; adopt has its own test root). Brief fields override derived values. A bad `brief_dir` fails loudly. `profile: generic` or `detecting` is refused in unattended preflight.
**D3 Project brief mode satisfies the gates by content, not shape.** Transcript pointer + `requirements.md`; one grill-trace per capability (`requirement_key` kebab slug, `evidence:["brief.md#<capability>"]`, `confirmed_by:"brief:<path>"` only with a valid approval); glossary via `write_context_term.py`; FR Names verbatim. Because the gate checks shape only, brief mode additionally checks **in code** that each evidence anchor resolves to a non-empty `brief.md` section and each dimension's text is non-empty.
**D4 Gates are real, in this order, without breaking the contract.** (1) Fix the validators first (A3). (2) Introduce the gate behind an **injectable seam** in `apply_phase_result` with enforcement **off by default**, reusing `validation_record.run_phase_gate` (already turns a crash into an ask-level issue and reports `checked`) extended with `split_id`; place it between the artifact guard and `freeze_splits`, only when `result.ok and cas_current` and the task is `in_progress` (a stale or double apply keeps its CAS/idempotent answer); pass `config.runId` explicitly (A4). (3) Migrate tests, then flip the default to enforcing (A5). On failure the gate returns a **non-mutating rejection** `{"ok": false, "reason": "phase_gate_failed", "issues": [...]}`; the task stays in progress. Master behaviour is specified, not implied: re-dispatch with an `issues[]` brief (phase-runner contract gains that input), a hard cap `MAX_GATE_RETRIES` on `loop_state.attempt`, and a terminal per autonomy level (guided: ask the human; autonomous: `mark_phase_failed` with the issues, recoverable through `single-session-recover`). A real v2 **override**: `single-session-apply --override-reason` (reason required, `normalise_override_reason`) runs the gate, then writes the override record and the completion under the same lock through a lifecycle hook; `constitution.md` ASK FIRST text and guide §7.5 are updated in the same diff.
**D5 Unattended policy, opt-in per gate.** `autonomy: unattended` is new. `auto-default` proceeds. An `orchestrator-approve` gate that is not constitution-locked auto-approves **only if the catalog carries a reviewed `unattended_answer` for it**, otherwise it escalates. Initial allowlist: `design.preview-approval`, `design.review-loop-finalize`, `design.upload-screen-mapping` (all three need a valid hash-verified package; the first two also the automated FR-coverage self-check). Anything else is added only by an explicit reviewed line in the B5 PR. `validate_catalog` gains its own checks (it ignores unknown keys today): no `unattended_answer` on hard-stop, constitution-locked, or **denylisted** gates. Denylist (explicit ids, pinned by a test): `build.migration-preflight-fail`, `build.migration-apply-fail`, `build.env-validation-missing-vars`, `deploy.missing-env-vars`, `deploy.post-migration-manual-steps`, `project.supabase-project-ref`, `build.browser-verify-prereq-unresolved`, `build.browser-verify-fix-exhausted`, `plan.validate-input`, `build.section-file-required`, `project.session-conflict`, the five `*.out-of-sequence-continue`, any `*prereqs-missing`; plus the constitution ASK FIRST "Skipping test layers". Constitution-locked and `hard-stop` gates always escalate. **Reviews:** `deferred` or `partial` → the master runs the missing passes and escalates only if they fail; `skipped`, or an absent `review_status` where the phase prescribes reviewers → escalate. Unattended build is sequential; the `section-builder` fan-out needs `allow_parallel_builders: true` in the package. A plain seed fails fast at preflight. **The design auto-approval is an FR change:** Spec Impact `modify` on FR-01.04 AC07/AC08 (minted by the producer), the pins are rewritten ("unattended resolution requires a valid package"), design `SKILL.md` and `references/review-loop.md` are in U3's touch set, an ADR records the reversal. Who answers: the phase-runner returns gate-pending; the **master/CLI** resolves it after the hash and FR-coverage checks. Default: **off** (`unattended_design_autoapprove: false`) until the §6 procedure passes.
**D6 Pending and escalation with no human.** Build on what exists: `mark_human_gate` and `paused_human_gate`. The task stays `in_progress`; **no new `PhaseTaskStatus`**. Add run status `needs_input` plus `gate_pending{gate_id, options, default}` in `run_config`, an event, and a distinct master exit. Re-entry = re-dispatch of the same task where the gate resolver returns the recorded answer for that `gate_id` (not a mid-skill resume). The transition lives in a lifecycle-sibling module that shares `_PhaseTasksLock`, is registered as an entrypoint (`LIFECYCLE_COMPLETION_ENTRYPOINTS`) and has an ADR (the documented invariant is that every phase-task mutation goes through the lifecycle). Readers that must understand `needs_input`: `resolve_next_dispatch` (`single_session_loop.py:132-153`), `_OK_NEXT_ACTIONS` (`single_session_cli.py:37`), `resume_run` (`single_session_recovery.py:123-143`), `_advance_loop_state`, `live_run_snapshot` (`phase_invocation_mode.py:146` — otherwise collision protection turns off), `generate_handoff_on_stop.py`, `update_build_dashboard.py`, `orchestrator_context.py`, `master_stop_check.py`, `run_config.v2.schema.json` run-status enum. Today there is no gate-pending result shape and the phase-runner has no AskUserQuestion tool; U2 defines it. Budget = counters in `loop_state` (retries, iterations, wall-clock); cost only in the external harness. **Consumer list for the autonomy value** is produced in B5 by `git grep -nE "autonomy|autonomous"` over `plugins/` and `shared/` (excluding worktrees), pasted in the PR, and must include at least: CLI choices (`cli.py:59,229`), `orchestrator.py:12`, schema enum (also adopt's `supervised`, `config_writer.py:197`), `inference.py`, `config_factory.py:143,284`, `step_planning.py:87`, `brief_intake._ALWAYS_ASK`, run `SKILL.md` and `references/brief-intake.md`, `autonomy-levels.md`, `single-session-gate-discipline.md`, build `references/code-review.md:168`, `autonomous-loop.md:3`, `first-actions.md:257`, `migration-safety.md:41`, `agents/section-builder.md`, deploy `SKILL.md:75`, test `agents/test-runner.md`, `references/step-1-unit-tests.md:17`, `step-3-playwright-e2e.md`, changelog `SKILL.md:144,252`, `constitution.md:73`, `check_destructive_migration.sh:7`, `iterate_stop_guard_transcript.py:136,139`. `unattended` behaves at least as autonomous in every site keyed on "autonomous".
**D7 Profiles come through the resolver.** Preflight resolves the brief's `profile` with `resolve_profile.py` (exit 2/3 = hard stop). `ux_shape` and `ui_host` are added to `stack_profile.schema.json` as **plain strings** and `ux_shape` is validated in preflight code; **no `enum` in the resolver** and no edit to `profile_resolver.py`.
**D8 Chat-first.** `ux_shape: chat-first` selects Layout D, `chat-map.json`, a pane-state screen for every chat-only capability (linked by the `<!-- Requirements: FR-xx.yy -->` comment injected after Project minted ids), flow mockups generated from golden paths, and upload mode re-entering the normal Design flow. Mockups stay untouched in `uploads/`; Design copies them to `screens/NN-name.html`. Chip classes must not use `nav-item`/`topnav-link`.
**D9 Screenshot verification is a blocking Test-phase check** (needs a running app and Playwright), not a design-approval gate. Metric and tolerance are defined in B3c; "separates a planted wrong screen from a right one" is a **hard acceptance gate** of B3c. Until the §6 procedure passes, D5's design auto-approval stays off.
**D10 Repo rules for every unit.** Docs in the same diff, edits localized and rebased on main; net-zero or smaller on grandfathered files, extract first; one pytest root per process; `uv run scripts/verify_local.py` and `uvx ruff@0.15.15 check .` before push; tests tagged with FR/AC **minted by the producers; no unit hand-picks FR ids or ADR numbers**; `validate_catalog` requires `covered_phases` to equal `COVERED_PHASES` so tuple and JSON change together, and the doc-sync test covers the re-rendered `.md`. A unit edits a test only if the test is in its touch set.

### B7: real end-to-end run through the WebUI

Purpose: prove that a Brief package turns into a working chat-first Shipwright application with a **real agent**, driven the way a person drives it, and leave a reviewable record. It is an **operator-started check, not a CI gate**: it costs tokens and wall-clock time, and a model run varies. The campaign builds the tooling; the operator runs it (see Acceptance).

- **Fixture package** (synthetic, committed under `integration-tests/fixtures/social-engagement/`, created in B3b and completed here; `approved_by: "fixture:social-engagement"`, usable only with `SHIPWRIGHT_ACCEPT_FIXTURE_APPROVAL=1`, which the spec exports into the WebUI server's environment so the agent inherits it): `ux_shape: chat-first`, profile `chat-first-json` (B4), `deploy_target: none`, `autonomy: guided` (the spec answers the gates through the WebUI; `unattended` does not exist before campaign U; `auto-default` is a gate-policy level, not an autonomy value). Recompute `package_sha256` with `brief_package.package_sha256` after every edit. The app is a small **social engagement desk**, written out in full inside the package because a runner cannot read anything outside this repo: a chat on the left, a pane on the right. Chat commands: fetch new matches, show a thread, draft a reply for a thread, mark a thread as posted, set keywords. The pane is a board with one tab per platform (Reddit, Hacker News, LinkedIn) and a status per thread (new, drafted, posted). Data is local JSON. **No external service is called**: matches come from a seeded JSON file and the reply drafter is a deterministic local function behind an interface, so the run needs no keys. The package contains a pane-state screen for every chat-only capability (D8) and a `chat-map.json`.
- **Expected-result checklist** (`expected-result.md` next to the fixture): the screens, requirements, profile, chat commands and pane states the finished app must show; each item is **hard** (must hold) or **soft** (recorded, compared by eye).
- **Spec project** (Playwright, a small Node project used only by this unit, placed at `integration-tests/e2e-webui/`, outside `plugins/` and `shared/` so packaging, `update-marketplace.sh` and the cache sync never see it; it has its own nested `.gitignore` listing `node_modules/` and `e2e-report/`; every `.ts` file stays at 300 lines or fewer because the bloat cap applies to TypeScript; child processes are started with fixed argv arrays, never a shell string built from env vars, to stay clear of Semgrep/CodeQL). It drives the WebUI as a **black box**, like a user. Facts about the WebUI that the runner cannot read from this repo (verified against the `shipwright-webui` checkout at review time; re-check them):
  - The WebUI is a separate checkout, located through `SHIPWRIGHT_E2E_WEBUI_DIR`. It needs `npm ci` in its `server/` and `client/` (a native `node-pty` build). The spec ships its **own stack starter modelled on** the WebUI's `client/e2e/isolated-stack.mjs` (server build, asset copy, client build, start with HOME/USERPROFILE and own ports pointing at a temp directory). It must **not** reuse that file's `prepareReadinessPrerequisites`, which seeds a fake plugin cache and a fake `uv` shim that would break real Shipwright scripts.

## 6. Closed-loop acceptance: an operator procedure, not a campaign unit

A campaign sub-iterate cannot do this (no Skill tool; headless runs need an explicit permission mode; fixes need merged PRs and a cache sync, which are operator steps; skill edits live outside the repo). It runs from a dedicated top-level session started by Sven, after U4, with budgets (iterations, wall-clock, spend) written down first.

**Decisions for Sven before the first run (not decided here):** the headless permission mode and the sandbox. A non-interactive run cannot answer prompts, so either a narrowly allowlisted mode or a broad-permission mode inside an isolated sandbox/container is needed; the second is a real security trade-off and must be a conscious choice.

1. Prepare the scratch project: plugins enabled, cache synced, package committed, `SHIPWRIGHT_ACCEPT_FIXTURE_APPROVAL=1`, Step 3/Step 1 answers pre-supplied by the package (they are AskUserQuestion points that block a headless run), no uncatalogued question reachable by the fixtures.
2. Run the harness `--autonomy unattended` on fixture 1, then fixture 2.
3. **Oracle (by the driver):** success iff `run_config.status == "complete"`, no `gate_pending`, no new `validation_overrides`, no `human_gate_pause` in `run_loop_events.jsonl`, and no AskUserQuestion tool_use or question-ending turn in the stream-json transcript. Anything else is a failed run.
4. On a failure: diagnose, fix through the normal iterate path (PR, review, merge), sync the cache, re-run. The loop never regenerates or approves a package. A defect in the private skill is fixed under the skill's own version control and reported; Sven reviews skill changes afterwards.
5. Success = two consecutive clean runs per fixture; the report lists auto-approved gates with their `unattended_answer`, escalations and spend. Tune the D9 tolerance here; only then turn `unattended_design_autoapprove` on.
