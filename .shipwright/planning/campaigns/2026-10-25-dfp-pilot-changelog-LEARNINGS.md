## 3. Recurring patterns

- The AI judges and code validates: the release-page condensation and (proposed) the upgrade-notes drop.
- A mixed section is the normal case: Step 4 and Step 7 each carry five to eight instructions of three classes, so a section is not the unit of conversion; the instruction is. The inventory therefore lists `parts` for a `mixed` section.
- Where two sources disagree, the prose contradicts itself more often than it contradicts the code (D1, D8, D10, D11): the code is the safer oracle, and the real-model runs decide the rest.

## 4. Pitfalls

- **A green test on a function the skill never calls.** The AC02 `covers` tests exercise `lib/changelog.py`, which no step calls; the ledger rated AC02 `enforced, tested` for months. Found by tracing the skill's own path from `SKILL.md` to the tool it runs, not by reading test names (finding D13; ledger row 2). The AC04 iterate had found the same shape once before.
- **The brief's own numbers and line citations go stale.** "Seven references" (there are ten), three moved line citations, a pre-assessment table that missed the event fold and the upgrade-notes check. Re-measure from the tree the unit starts on, and let a checker hold the citations.
- **A checker test on the real tree is a CI pin.** A first version of the checker's tests also ran it on the real skill; the spec reviewer pointed out that CI runs that test root, so every prose edit would red CI and the ADR's claim "out of CI" would be false. The tests now use throwaway skills only; the pilot's units run the CLI on the real one. The same review caught a `covers` mark on that test (a ritual tag, the D13 mistake).
- **A review can reject what the operator approved.** The architecture review rejected the inventory checker that the brief and programme P10 mandate; the unit halted until the orchestrator overruled the reject by pointing at the brief. Brief the reviewers with the approved scope, or expect one halt per unit that builds a mandated mechanism.
- **Data a conversion tool needs does not belong under `plugins/*/skills/`.** The three inventory data files were first filed next to `SKILL.md`; the PR-review sensitive-path rule blocks new content there even though nothing reads it at runtime, which cost one PR-review round and a move. File such data with the campaign reports.
- **A seam that can publish needs a second, independent guard (P1).** The first guard keyed only on a marker sentence in the notes; both external plan reviewers and the internal architecture reviewer pointed out that a lost or quoted marker is then the only defence. The guard now also refuses whenever the fixture-model variable is set without the `gh` seam, and the marker is a hard-to-collide token.
- **"Offline" has to be proven with the network actually blocked (P1).** The scratch-project proof sets `UV_OFFLINE=1`, a dead proxy and no keys; a test that merely runs on a warm machine proves nothing. Its one soft spot is the pyyaml fetch of `uv run --with pyyaml`, so the test warms uv's cache first and skips only when that fails.
- **A `.cmd` shim cannot be a `gh` stand-in on Windows (P1).** `gh` is spawned as `["gh", ...]`; the seam is an argv prefix read from a JSON array (shell-style splitting mangles backslash paths), and a malformed value is refused instead of falling back to the real `gh`.
- **Two identical scratch projects still differ (P2a).** Run the same build twice in two directories and diff the traces before trusting a recorder: the first diff showed compact timestamps in run ids (`project-20261117-125101955883`), Windows backslashes after a path label (so a Windows trace would never equal a Linux one) and files the last phase rewrites after its own commit (an unclean start tree). The byte-identical-twice test is the cheapest guard a normalizer can have.
- **An environment allowlist is not enough on its own (P2a).** Both plan reviewers asked for the same three extras: a seeded credential VALUE must not survive (not only the name), the user's git config and hooks must not reach the scratch (a hostile global config with a failing `pre-commit` and `commit.gpgsign` is a test), and the parent process environment must stay untouched. `minimal_valid_project` runs git under the process environment, so the builder swaps HOME for the duration of its calls.
- **A freeze test cannot tell an unstarted freeze from a deleted lock (P2a).** No lock file reads as unfrozen, so the stop-2 iterate must be reviewed for the lock's existence; the check itself (changed, missing, unlocked trace, delta that does not name exactly the change) is tested on synthetic trees.
- **Do not tag a harness test with a requirement it does not exercise (P2a).** Only the test that runs the real release script against the stub carries `covers FR-01.09/AC14`; the other harness tests carry none (the ritual-tag mistake of P0).
- **Run the prose literally and the findings appear (P2b1).** The first full replay of Step 6 failed three ways before any scenario asserted anything: a pathspec naming a directory the project has no tracked file in (D21), a tracked drop whose deletion the pathspec leaves out (D22), and an event recorded by Step 5.5 that nothing commits (D23), each ending at the audit's "dirty working tree" refusal. Prose that works for a model that improvises does not work for a replay; the replay records the refusal as today's behaviour and the findings file carries the decision to the operator.
- **A trace that must be equal on two operating systems needs a short list of fields (P2b1).** Step output keeps only whitelisted facts; error text, absolute paths and tool output stay out of the trace and are asserted in the scenario instead. Both layouts of the events log are separate traces only where they differ (S1, S2); the rest have one.
- **Citations are data, the lines are checked (P2b1).** `CITES` maps each replayed command to its `SKILL.md` line and a needle; a test fails when the live line no longer holds it, and a second test keeps the table and the driver's command keys equal. P5 (thin `SKILL.md`) will red the first test on purpose: it must point at the pinned prose copy of stop 2 by then.
- **Check `git status` through a function that does not strip (P2b1).** `strip()` turned ` D path` into `D path` and a wrong expected value took three runs to find.
- **Make the oracle prove that a scenario used it (P2b2).** `Scenario.acs` lists the ACs a scenario is tagged with and `verify` fails when the oracle never judged one of them (`oracle.ASSERTED`). The first run of that rule caught S1 asserting its version outside the oracle. A scenario check that compares a literal is not the oracle, however it is named.
- **A refusal is judged by its kind, not by its exit code (P2b2).** Every refusal scenario names the tool's own word (`verify_mismatch`, `content_floor`, `unsupported_format`, the audit's dirty-tree sentence), read from the tool's JSON where it has one. A message that an operating system words (a missing program) is asserted by exit code only.
- **Seed the regression into the instrument, not into the product (P2b2).** The three seeded regressions swap one frozen command or one step of the replay and run the scenario that must notice (`test_seeded_regressions.py`); each asserts the oracle's own message, so a crash further down cannot pass for a catch.
- **A coverage check needs a table that fails when it goes stale (P2b2).** P8a-c are three small functions over the inventory, the prose and the scenarios; each test has a twin that feeds it a broken input and expects red, because a check that cannot go red is not yet a check.
- **A hash over `ast.dump` is not a hash of the test (P2p).** `ast.dump` prints fields that exist only in some interpreter versions (`type_params` from 3.12), so a lock written on one Python would read as a change on another. The helper serializes the tree itself and leaves out empty fields and positions; a test pins that no version-specific field is in the output.
- **A fingerprint that follows helpers must also follow constants and fixtures (P2p).** Hashing only the test body missed an assertion inside a helper (MEASURE section 4); including functions fixed that, but a threshold held in a module constant and a fixture in `conftest.py` were still outside. The helper now follows names to module-level constants, classes and functions and requests to fixtures (a `conftest.py` is handed in; a plain function there is not reachable by name). Known limit: a helper imported from another module is not followed, which is why those modules are frozen files themselves.
- **A promise can be red by design (P2p).** AC11 (nothing is published before the request is merged) is false today in guided and driven runs (D2) and true in autonomous ones, so no single driver test can be green for all modes. The list says `gap` for the whole promise and carries a separate passing entry for the half that holds; it never claims the whole.
- **Name the meta test so a glob over promise tests cannot catch it (P2p).** The test that checks the promise list was first `test_promise_list.py`, which the rule 'every `test_promise_*.py` is a promise test' then counted as a promise test; it is `test_promises_meta.py` now.
- **The statuses of a promise list must be checkable, not just written (P2p).** A test compares the claimed status with what exists: a named test that is missing makes the claim `passing` false, and an entry with no check can only be `gap` or `proposed`.
- **Typed heredocs corrupt files with quotes and backticks** (a Python script with an apostrophe in a string ended the heredoc early): write scripts with the Write tool.
- **A hash that follows names must follow every binding of a name, not the winner (promise-hash hardening).** The first fingerprint looked a name up in a def table first, so `h = lambda: None` after `def h` changed what the test runs and kept the hash. One ordered list of all bindings (defs, constants, imports) per name closes that whole class at once; the same shape fixed the import alias swap, because an import is just one more binding. Test each blind spot by writing the swap that would have hidden it, red first.
- **What pytest applies without being named is part of every test (promise-hash hardening).** An `autouse=` that is anything but the literal `False`, and any `pytest_*` hook, run for every test; the conftests above the golden root and the package markers do too. Freezing those files in `REQUIRED` was cheaper than hashing them into each closure, and it keeps the root `conftest.py` from moving every promise hash.
- **One helper for what two readers must agree on (promise-hash hardening).** `covers_of` and `Module` each read `pytestmark` from plain assignments only, so `+=` or an annotated assignment lost the AC id in one and the marks in the other. A single target-extraction helper makes them agree by construction.
- **Pin a literal digest, and compute it on more than one interpreter (promise-hash hardening).** The hand-written serialization is only as portable as a test says it is: one f-string-heavy fixture pinned to its sha256 came out identical on 3.11, 3.12 and 3.13. A weaker check (hash equals hash) cannot see drift.
- **A test that cannot fail is a note, not a promise (promise-hash hardening).** The aggregation half of AC11 can only fail if someone adds an outward command to that step, and the whole-release preview of AC10 is a person's choice the driver never sees. The honest fix is to say so in the list (a trivially held invariant, a narrowed sentence), not to make the sentence bigger than the test. Where a refusal test checked 'no None', the exact committed map (`1.2.0` for the stale manifest) is what proves the run was refused for the right reason.
- **An import alias is a decision, not a style (promise-hash hardening).** Hashing the binding makes an alias swap visible, but the meta test must also refuse any alias that differs from the imported name, or `ss` can quietly stand for another module. The promise tests now write `scenario_support.x` in full.
- **A full-model baseline before the lock is cheap insurance.** 43 runs (one per scenario and layout, Opus subagents in throwaway projects) gave 26 A, 7 B, 0 C, 8 D, 2 E: the model follows the prose, every difference was a prose, replay or harness defect, and the lock went in with no approved delta. The findings (F1-F14) became the extraction work list. Generic tool from it: `shared/testkit/golden_lock.py` writes any plugin's golden and promise locks (`--plugin`), so the next pilot reuses the freeze step unchanged.

## 7. Ideas from outside, to test against the pilot (added 2026-11-16, not decisions)

Source: a read of NVIDIA NeMo Guardrails and its Colang 2.0 runtime (github.com/NVIDIA-NeMo/Guardrails, develop branch; flow parser, `runtime/flows.py`, `runtime/statemachine.py`, `tests/utils.py`, `nemoguardrails/testing/chat_harness.py`). Colang guards a chat between a user and a bot at run time; it is not our guardrail problem and we do not adopt it. Three of its design ideas fit the CLI steps of P3 and P4. The pilot should say at the end (section 2 or 3 of this report) whether each one held.

1. **A process as data.** Colang parses a flow into plain data (dataclasses with a `_type`), lowers it to a flat list of steps with labels and jumps, and can dump that list as JSON before anything runs. For us: the step order and allowed transitions of a skill as a JSON step list. Question for the pilot: does `release.py` end up with a step list that a validator can check without running it? Colang's weakness to avoid: a misspelled flow name fails silently, and there is no separate validator. We validate in Python before anything runs.
2. **Paired lifecycle events.** Every action has a command (`Start`, `Change`, `Stop`) and results (`Started`, `Updated`, `Finished`, `Failed`), a uid, and an explicit status (initialized, starting, started, stopping, finished). For us: each CLI step reports started and finished (or failed) with a step id, so a checker can name the step a run skipped. Question for the pilot: can the golden traces of P2a be written as these pairs, and does that make the "skipped step" failure readable? The CLI as a pure function (state plus event in, new state plus events out) is what makes the trace replayable.
3. **The model only at declared seams.** Event matching, lifecycle and priorities are plain Python; the LLM is used only through opt-in steps, and its output must come back as a typed event the engine validates. An event nobody handles is emitted explicitly. For us: this is the line between the CLI and the questions in the thin `SKILL.md` (P5). Question for the pilot: does every answer the model gives come back through a typed value the CLI checks?

Also noted from their tests, for P2a and P2b: they compare event lists as an ordered subset with exact length, drop volatile keys (uids, timestamps), and feed scripted model answers in order. Our golden files are recorded, theirs are written by hand, so ours is a step further. Colang 2.0 is documented as beta, and open issues name rails that fail open on missing globals. That is another reason not to depend on it.

Older workflow tools (state machines, BPMN, job schedulers) have the same shape, so none of this is new. The pilot is the cheap test of whether it pays for skills.

## P3 (2026-11-23): CLI part 1

1. **Steps and effort.** P3 took two runner attempts (the first built the draft, the second reviewed and froze it) because the keyword classifier said `large` and the operator had to accept it. Biggest time sinks: the changelog test root takes about 15 minutes (43 scenario replays plus the same 43 through the CLI driver), so every full re-run is a decision; and the freeze bookkeeping (4 deltas, 4 promise anchors, 3 inventory files) cost more than the CLI.
2. **Code or AI decisions.** The F1a/F1b/F4 branching is a git question (branch kind from the run state, release commit on the base, event-only HEAD), so the CLI decides; but a push is an outward command, so it stays one literal line the release guard hook can read (BRIEF section 2, programme P4). The first delivery moved the push into the CLI and the independent reviews rejected it: a decision may move into code, an outward command may not (FINDINGS D39, option B).
3. **Recurring patterns.** The CLI returns every tool's own stdout/stderr/exit (`commands`) so a golden driver can replay them into the old trace shape: the trace stays an equality and the CLI stays a pure wrapper. An injectable runner gives L1 tests without a subprocess.
4. **Pitfalls.** A state file written into the working tree is a side effect the dirty-tree guard sees. A frozen table keyed on headings breaks on any prose move. A keyword classifier reads words, not diffs: three risk flags (`auth`, `rls`, `migrations`) fired on the words of a changelog spec.
5. **Tools.** `golden_lock.py --check` (generic, stdlib); `check_skill_inventory.py` (Shipwright-specific data files, generic idea); the injected-runner pattern (generic).
6. **Doable by a stranger?** Yes, given the P4 notes and D39-D41; the one real decision (option B, the orchestrator chose it) is written down for stop 3 as "operator may amend". Two lessons from the fix round: a rule that two places must apply (the hook and the CLI) lives in ONE stdlib file loaded by both, with a real-git test over the history shapes, not a copy with a promise; and a "wait" decision needs ONE key, tested over all (mode, autonomy) pairs, or the prose, the verify and the CLI drift apart.

## P4 (2026-11-23): CLI part 2

1. **Steps and effort.** Four subcommands (`sync`, `commit-and-tag`, `record-event`, `close-phase`), the closing verify and the fix list of P3 took one run; the larger cost was the golden harness: a CLI driver that chains several CLI calls into the log entries the frozen traces know, and a dozen scenario checks that changed with the operator decisions (F1b, F4, F6).
2. **Code or AI decisions.** Everything that was a shell chain with a stop rule (`&&`, commit before `HEAD`, tag only on exit 0, push on a feature branch only) is code now; the outward commands (`gh pr create`, `gh pr merge`, the tag push, the release page) stay literal one-liners, because the operator reads them and their failure is a decision (stop, F4).
3. **Recurring patterns.** Injected runner plus a recorder for L1 tests, real git plus the gh stub for the decisions; a decision that changes behaviour gets one test per driver (replay shows the old flow fails it, CLI shows the new one passes).
4. **Pitfalls.** A promise test that runs the whole flow must now say `autonomy` (a guided flow stops before the tag, F1b). The live-prose behaviour test that executed the fenced Step 7 blocks had to move to the code (`test_release_event_real_git.py`). Deleting a skill heading breaks `promise_list.json` anchors (`startswith` match on the heading): keep the old heading words. Adding a `mechanic` row to `inventory.json` demands scenario mapping in the frozen `coverage.py`, so P4 left the inventory as planned.
5. **Tools.** `golden_lock.py --promise-only --repin` prints the sha pair for the `promise.lock.json` delta; `SHIPWRIGHT_GOLDEN_REGEN=1` rewrites traces (stage only the ones whose content changed: the rest differ by line endings).
6. **Doable by a stranger?** The CLI and its tests: yes. The delta bookkeeping (one entry per frozen file, `before` is the lock sha, the lock re-pinned first): only with the notes above.

## P4b (2026-11-24): release guard hook

1. **Steps and effort.** One hook, one command parser, one registry row, three test files (parser, real git, integration). The parser took the most thought; the hook itself is short. The changelog test root (576 tests) takes about five minutes, so run it once at the end, not per edit.
2. **Code or AI decisions.** All code: whether a command is an outward release action is a lexing question, and whether HEAD is the release is a git question (record commit, ancestor, event-only diff). Nothing here needs a model.
3. **Recurring patterns.** A hook that fires on every Bash call parses with `shlex` in non-POSIX mode (a Windows path keeps its backslashes, quoted text stays one token), runs no git call until a command is a candidate, and fails open on any error. The producers (`release_runstate.save`, `release_commit.write_state`) write the state in the tests, so the hook is tested against real bytes.
4. **Pitfalls.** The brief says the record must be "for HEAD", but `record-event` adds one event commit after `commit-and-tag`, so a strict equality would block the very flow the skill prescribes. The hook accepts HEAD when it is the record commit or descends from it through commits that touch only the event files. Never-ending "in progress": the run state is never deleted, so the hook also asks `origin` whether `v<version>` is out (only on a would-be deny) and goes inert when it is. `docs/hooks-and-pipeline.md` is CRLF in the working tree and LF in the index: edit with newline="" and match the line ending.
5. **Tools.** None new. `golden_lock.py --check` stayed green with no delta (hooks.json and the hook script are not frozen).
6. **Doable by a stranger?** Yes: the spec names the files; the two judgement calls (event-commit descent, the origin tag check) are recorded in FINDINGS D34.

## P5 (2026-11-24): thin SKILL.md, pins moved, F7 prose removed

1. **Steps and effort.** Smaller than the table says: P3 and P4 had already done most of the thinning, so P5 was the leftovers (F7 mentions, history sentences in four references), one subcommand (`push-tag`), one public wrapper, the pin map and the delta bookkeeping. The 73-test CLI-driver run takes about seven minutes: start it early and let it run while writing prose and tests.
2. **Code or AI decisions.** The F1a/F1b/F4 branching is a git question (branch kind from the run state, release commit on the base, event-only HEAD), so it is code; the model keeps `gh pr create`, `gh pr merge` and the release-page call. The price is that the release guard hook cannot see a push made inside the CLI, so the CLI repeats the hook's rules (FINDINGS D39).
3. **Recurring patterns.** A decision moved into code keeps its old test against the prose only as a pointer ("the skill calls the subcommand, in this order"); the behaviour is proven in-process with the injected runner and once on real git through the CLI driver. A driver that replays a step through the CLI has to drop the CLI's own git queries from the log, or the logged entries stop matching the prose's.
4. **Pitfalls.** The first version of `push-tag` demanded a merged PR in every mode and broke S13: a driven run never merges its PR and the frozen trace pushes the tag with the PR open (`mode` decides, not `autonomy`). After `gh pr merge --delete-branch` HEAD is the trunk, so the branch kind must come from the run state `record-event` kept, never from `git rev-parse HEAD` at push time. A "history" sentence in a reference ("since unit P4 ...") is a delta per file in the frozen prose: batch them.
5. **Tools.** `golden_trace.file_sha256` computes the `after` of a delta (CRLF read as LF); a second delta with the same `before` and a new `after` keeps the earlier reviewed entry and still satisfies the check.
6. **Doable by a stranger?** Yes, given the P4 notes and D39-D41: the one real decision (keep the push in the CLI or keep it literal) is written down for stop 3.

## P6 (2026-11-24): the ratchet

1. **Steps and effort.** One checker (300 lines), its registry, 69 in-process tests in two files, one `(gate)` step in `ci.yml` and in `verify_local.LOCAL_GATES`, four doc edits and one baseline number.
2. **Code or AI decisions.** All code: what counts as a shell block, a chain or a new command is decided by the checker; nothing is left to a reviewer's reading of the prose.
3. **Recurring patterns.** A gate over a frozen file keeps its allowances in its own registry (FINDINGS D45). The drift test needed no change because the gate step name is the join key.
4. **Pitfalls.** A quote-aware scan is needed for chains (`"a | b"` inside a flag value is data), and `2>&1` must not read as `&`. The CRLF docs need a line-ending-preserving edit.
5. **Tools.** `diff_risk_recheck.py` exits 3 on any `ci.yml` edit, however small; plan for the ack before the unit starts.
6. **Doable by a stranger?** Yes; D45 and D48 are the two things an operator has to decide.
