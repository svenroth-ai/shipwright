# The autonomous release merge picks its method, pins the head, stops when the base moved

Run: `iterate-2026-11-28-u4-autonomous-merge-method` · campaign `dfp-changelog-followups`, unit U4 · FINDINGS D110 (new D116) · FR-01.09.AC16 (added, auto mode).

An autonomous hand-invoked release ran `gh pr merge --merge --delete-branch`, which this squash-only repository refuses. Now SKILL.md Step 7 asks `release.py merge-ready` (`lib/release_merge.py`) and runs the one literal line it prints, `gh pr merge --{method} --match-head-commit {head} --delete-branch`. merge-ready never merges and never changes repository settings. It answers `ok` only for a hand-invoked autonomous or unattended release on a feature branch whose HEAD is on the release branch and is the release commit or its event commit (`release_descent`, the guard's rule), whose open PR's head on the host is that same commit and whose PR still targets the recorded base. The method comes from `gh repo view --json mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed`: a merge commit when allowed (the tag stays on the release commit), else squash, else rebase (push-tag proves either after the merge, U3). Before a squash or rebase the base is fetched (FETCH_HEAD only, `release_verify.fetch_base`, extracted from `on_base` with the same command keys) and must be an ancestor of the head; otherwise it refuses with `base_moved` and a plain restart message: nothing merged, no `gh pr update-branch`, no automatic re-creation (operator decision 2026-11-28). Every read failure is a refusal with its own reason, never a fallback to `--merge`. The push URL's user and token never reach the answer. The release guard already judges the line correctly (`--match-head-commit` takes a value, so the line is this release's merge, judged by HEAD): it allows it during a release and denies it once HEAD moved. The guided `waiting_for_merge` text says to merge while the branch is up to date with the base.
