# A pipeline phase can wait for an outside event (the release pull request merge)

Run: `iterate-2026-11-28-u5-pipeline-waits-for-merge` · campaign `dfp-changelog-followups`, unit U5 · FINDINGS D110 · FR-01.01.AC39 (added, auto mode).

Operator decision 2026-11-28: a pipeline-started release also waits for its pull request to be merged before tagging. A phase result could only be `ok` true (the lifecycle marks it done and plans the successor, so deploy runs and the tag lands before the merge) or false (strict-stop, the run is failed). This unit gives the single-session loop a third answer, inert until U6 makes the changelog phase emit it.

**Shape.** A phase-runner result may carry `waiting: {"reason": "waiting_for_merge", "pr_url": "https://..."}` (`single_session/result_contract.py`): only `WAITING_REASONS` exist, only the phases in `WAITING_PHASES` (today `changelog`) may report them, the result must be `ok: false` with the usual `reason`, and the link must be a plain https URL with a host (`PR_URL_RE`, no space, control or escape character). Because the result is `ok: false`, an applier that does not know `waiting` strict-stops instead of completing the phase and running deploy.

**Where the hold lives.** Not in `shipwright_run_config.json` (no schema value; the WebUI reads that schema, and a new status would be an operator decision) but in the loop state `.shipwright/run_loop_state.json`, as a `waiting` marker keyed to run id + phase task id + the task's CAS version: the same pattern as the existing `gateTerminal` marker (`loop_state._current_marker` is now shared by both). The phase task simply stays `in_progress`. `orchestrator_pkg/single_session_wait.py` owns the three beats:

- **apply** (`apply_waiting`, routed from `single_session_apply` after the override check): refuses a stale version or session (exit 2), a task that is not open, a task whose own phase may not wait (`waiting_phase_mismatch`), and an unreadable loop state (fail closed); otherwise it writes the marker, resets `attempt` / `gateRejections` (a waiting pass is a finished pass, not a retry), emits the loop event `phase_waiting`, completes nothing and plans no successor. The result's summary and artifacts are not stored. Any other result for that same dispatch (held or released) is refused `held_for_outside_event` (exit 2): the phase finishes only through Resume and a fresh dispatch that re-checks the merge (doubt review).
- **next** (`waiting_action`, in `resolve_next_dispatch` after `ask_human`): answers `action: "waiting"` with the link, the task and a plain `next_step`; claims nothing. The CLI exits 0.
- **resume** (`release_waiting`, in `single_session_recovery.resume_run`): the card carries a stable `waiting` block; `--confirm` flags the marker `released` (kept, so a replayed result of that same dispatch is refused `stale_version` instead of re-holding) and the next `single-session-next` re-dispatches the same task with a rotated version. A recover bumps the version and drops the hold too.

The master's Stop hook prints a PIPELINE WAITING banner with the link (re-checked against the same pattern, held markers only) and the two escape commands for a pull request closed without merging. SKILL.md and `single-session-loop.md` tell the master to end its turn on `waiting` in every autonomy mode and never confirm the resume itself; `phase-runner.md` states the contract U6 builds against: a phase that reports waiting checks the outside state itself when re-run and reports `waiting` again or `ok`, never repeating its outward work.

Known limits (disclosed): run_config shows the task only as `in_progress` while it waits; the phase's measured duration includes the wait (one `phase_started` / `phase_completed` pair); a lost loop state loses only the hold, the task is then re-dispatched and the phase reports waiting again. There is no cap on repeated waits: each round needs a person's Resume.
