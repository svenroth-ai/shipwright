# Keeping Token Cost Controllable

A lookup, not a report. Find the band that matches your project's own numbers,
do the two or three things listed for it, and stop — the rest of this page is
for a different situation than yours.

## The number to check first

**Decision-history size** — how big `.shipwright/agent_docs/decision_log.md`
actually is. This is the number the bands below key on; measure it directly
rather than estimating it:

```bash
wc -c .shipwright/agent_docs/decision_log.md   # bytes
wc -l .shipwright/agent_docs/decision_log.md   # lines
```

```powershell
(Get-Item .shipwright/agent_docs/decision_log.md).Length   # bytes
(Get-Content .shipwright/agent_docs/decision_log.md).Count # lines
```

The bands are also expressed as a rough iterate count, for the case where you
know roughly how many `/shipwright-iterate` runs a project has behind it but
haven't measured the log itself. That count is a weaker signal — how many
decisions get logged per iterate varies a lot by project (see "What's specific
to this repo" below), and this repo's own `iterate_history` field in
`shipwright_run_config.json` is legacy and stays empty; if you want an actual
count, `grep -c '"type": *"work_completed"' shipwright_events.jsonl` is the
reliable source (the loose spacing matches both compact and spaced JSON —
this repo's own event log has both). **Whenever the two disagree, trust the
byte/line count** —
it's what's actually loaded into a session; the iterate count is only ever a
proxy for it.

## Bands, at a glance

| Your numbers | What's happening | What to do |
|---|---|---|
| Decision history over ~35 KB (roughly 20+ iterates) | Nothing broken yet — this is a "before it bites" mark | [Set an explicit auto-compact window](#decision-history-over-35-kb--set-an-auto-compact-window-early) |
| Decision history over ~100 KB (roughly 60+ iterates) | The log is still small enough to be read in full every session — so every session pays to read all of it | [Confirm the index is doing its job](#decision-history-over-100-kb--an-index-starts-paying-for-itself) |
| Decision history over ~2,000 lines (roughly 150+ iterates) | A single-file read can no longer return the whole log, full stop | [Confirm you're on index-plus-detail-on-demand](#decision-history-over-2000-lines--the-full-file-can-no-longer-be-read-at-all) |
| A session runs a few hundred exchanges | Per-exchange cost compounds over a long conversation | [Spend reasoning effort and model tier deliberately](#sessions-running-long-a-few-hundred-exchanges--spend-reasoning-effort-and-model-tier-deliberately) |
| Any size | — | [What's not worth optimizing](#any-size--whats-not-worth-optimizing) |

## Decision history over ~35 KB — set an auto-compact window early

**Trigger:** the decision log past ~35 KB (roughly 20 finished iterates, at
this repo's own logging density).

**Symptom:** none yet, visibly — everything still works. This band is about
getting ahead of the next one, not fixing something broken.

**Action:** set `autoCompactWindow` explicitly (in `~/.claude/settings.json`,
or the project's `.claude/settings.json` / `.claude/settings.local.json`)
instead of relying on Claude Code's own default. Size it to the model's real
context window, not a guess.

**Trade-off:** compacting earlier is cheaper per session, but the first
auto-compact must not land in the middle of a phase whose state exists only in
the conversation — mid-interview, between a plan and its approval, between a
build step and its commit. Pick a window wide enough to clear the phase, or
make sure the phase checkpoints its own state to a file before that point.

## Decision history over ~100 KB — an index starts paying for itself

**Trigger:** the decision log past ~100 KB (roughly 60 finished iterates, at
this repo's own logging density).

**Symptom:** the file is still small enough to be read in full — so it *is*
being read in full, every session (a log you don't actually load in a given
session costs nothing extra for it; this band is where you cross into loading
it), which makes it a measurable share of every session's cost even though
nothing is failing.

**Action:** a Shipwright project's decision log already gets this treatment
automatically — `.shipwright/agent_docs/decision_log_index.md` (title +
one-line summary + anchor, per entry), regenerated by the same tooling that
writes to `decision_log.md` and read by default instead of the full log (see
`references/context-loading.md` in the iterate skill). If it looks stale or
out of sync, refresh it by hand:

```bash
uv run shared/scripts/tools/rebuild_decision_log_index.py --project-root .
```

For any *other* always-loaded file that's grown this large and has no index
of its own — a knowledge base, a growing conventions doc, anything a session
reads in full every time — this is the band where building the same kind of
index (compact summary + anchor per entry, full detail loaded only on demand)
starts paying for itself.

## Decision history over ~2,000 lines — the full file can no longer be read at all

**Trigger:** the decision log past ~2,000 lines (roughly 150 finished
iterates, at this repo's own logging density).

**Symptom:** it has silently stopped being read at all, index or not. A
single file-read call returns at most 2,000 lines — past that point, a "read
the whole file" instruction is not being followed no matter how it's worded,
because the tool call underneath it cannot return more.

**Action:** index-plus-detail-on-demand is no longer optional at this size —
it's the only way any of the content past line 2,000 gets seen. Shipwright's
own iterate context-loading step already enforces exactly this for
`decision_log.md` (index by default, full entry only via a targeted grep or
an offset/limit read once the index points at it). For a file of your own
without that structure, the fix is the same one: an always-loaded index, and
the full detail loaded only on demand. Writing "read it all" into a prompt
does not change what the read call can return.

## Sessions running long (a few hundred exchanges) — spend reasoning effort and model tier deliberately

**Trigger:** a single session runs to a few hundred exchanges, independent of
project size.

**Symptom:** cost compounds per exchange as accumulated context grows, on top
of whatever the decision/event history contributes.

**Action:** lower the reasoning-effort level for long-running sessions. Split
cheap and expensive work across models — a faster/cheaper tier for routine
building, a stronger one for review — **as separate subagents**, never as a
model switch mid-session: switching models drops the cached prompt prefix, so
the next turn re-pays cache-write rates on context that had been reading at
much cheaper cache-read rates. Run the cheap and expensive passes as distinct
calls instead.

## Any size — what's not worth optimizing

The decision log and the event log are not what makes a session expensive.
Cost tracks the *number* of exchanges times how much context each one
carries — not the size of any one file on disk. A large decision log you never
read in a given session costs nothing extra for that session; a short session
with a huge tool-call count can cost more than a long one with a lean history.
Don't spend a week trimming a log file expecting it to move your bill — it
won't, unless it's actually being loaded.

## What's specific to this repo, what transfers

The KB/line numbers above come from measuring *this* repository's own
decision log: **~1.7 KB per decision entry**, roughly 13 lines per entry —
both measured directly off `decision_log.md`. The iterate-count figures in
parentheses assume roughly one decision entry per finished iterate, a
simplification for the sake of a second lookup key; this repo's own actual
average runs a little below that (roughly two decision entries logged for
every three finished iterates, not one-for-one), so in practice this repo
needed *more* iterates than the iterate-count column implies to reach each
line. That's exactly why the byte/line count is the number to trust when the
two disagree, and why you should re-measure your own file's ratio rather than
assume this repo's holds for yours — a terser or more verbose logging style,
or a project that logs more or fewer decisions per change, shifts every
number in this page proportionally.

What transfers regardless of the exact numbers: the *shape* of each band —
get ahead of compaction before it's forced, add an index once a file is
sizeable-but-still-fully-readable, and confirm you've moved to on-demand
loading once it isn't fully-readable at all. That progression holds for any
growing always-loaded file, not just this one.

## Measure your own

Shipwright ships opt-in, operator-run tooling for the session-cost side of
this — see [docs/guide.md § Quality and Safety](guide.md#9-quality-and-safety)
for the full hook picture, or [Appendix B](guide.md#appendix-b-command-reference)
for the complete command list:

```bash
# This session's totals and per-phase breakdown
uv run shared/scripts/tools/context_cost_summary.py show \
  --project-root . --session-id <id>

# The same checkpoint-recommendation heuristic build/run already use,
# against measured cost instead of a raw tool-call count
uv run shared/scripts/tools/estimate_context_pressure.py --source context-cost

# Is checkpointing actually configured to fire, before it's needed?
# --model/--effort are both optional -- add them for a precise answer,
# e.g. --model claude-sonnet-5 --effort high
uv run shared/scripts/tools/context_cost_readiness.py
```

`context_cost_readiness.py` deliberately does not guess a default for you —
Claude Code does not expose the active model or effort level to a script, and
guessing would be worse than an honest "unknown." Pass `--model`/`--effort`
explicitly for a precise answer; omit them and it still reports whatever it
*can* see (whether `autoCompactWindow` is set at all). A `statusLine.command`
pointed at `context_cost_statusline.py` gives the same read as a running
`$cost (N calls)` in the prompt line instead of an on-demand check.

None of this sets anything on your behalf. `autoCompactWindow` and the
reasoning-effort level are your own Claude Code settings; a plugin cannot set
them for you any more than it can edit your personal
`~/.claude/settings.json` unasked. The model-tier split for build vs. review
is available via `shipwright_model_config.json` (roles `execution`, `review`,
`plan_review`, `finalization`; every role defaults to `inherit` — the
session's own model — until you set one). These are recommendations to apply
yourself, sized to the numbers you measured above, not defaults this page
ships on your behalf.
